## 1. Choose the exact app code

**Source code** is the set of files that make the app. A **Git commit** is a saved snapshot of those files; its commit ID identifies that exact snapshot.

A **branch** is a movable name for a commit; new commits can move the name forward. A **repository** (repo) is a project folder Git tracks with its saved history.

A **fork** is your own copy of someone else's Git repo. A **submodule** links to another Git repo and records which exact commit this repo uses.

**In this project:** the Project 3 repo points to VProfile source through `vprofile-src`. Pinning a commit means each build can use the same app version. Changing the pointer selects a different version.

A submodule stores an exact commit ID, not a branch name. `git ls-remote` lists references advertised by the remote, so not seeing a commit ID there does not prove that the commit cannot be fetched; a commit that no retained reference points to may later become unavailable.

Different VProfile branches may use different Java versions. Java is the programming language used by this app. Earlier read-only checks identified `origin/local` and `origin/atom` as Java 17 WAR candidates, and `main` and `ci-jenkins` as Java 8 candidates. A branch name does not prove the app builds; inspect its files and build it before choosing. A Git reference (ref) is a name, such as a branch or tag, that points to a commit.

The VProfile app was made by the instructor, not by the author of Project 3. Earlier checks found no license file on `atom` or `origin/local`, and no license text in `README.md` or `pom.xml`. Missing license text does not grant permission. Keep attribution and do not share a built WAR publicly unless permission is established.

**Useful checks:** `pwd` shows the current folder. `git rev-parse --show-toplevel` prints the Git repository root. `git submodule status` shows the submodule commit. `git ls-tree -r --name-only <ref>` lists tracked file names at a commit without switching to it. A Git remote is the saved address of another copy of the repo; `git -C <repo> remote get-url origin` shows that address. A search only tells you about the folders it searched.

## 2. Build the app and make sure its tests run

**Maven and its POM:** Maven is a tool that builds Java apps. POM means Project Object Model; `pom.xml` lists build settings and dependencies (libraries the app uses). The instructor supplied VProfile and its POM; developers normally maintain the POM for an app they own. In this project, the script edits the copied POM in `build-work/`, not the pinned file in `vprofile-src/`; Maven packages the app as a **WAR** (Web Application Archive, a packaged web app file).

**Why test count matters:** An earlier Maven run reported `BUILD SUCCESS` but ran 0 tests because the app's tests use JUnit 4, a Java testing tool, while Maven had only the JUnit 5 test engine (the part that finds and runs tests; see the caution below). JUnit Vintage lets the JUnit 5 test system run JUnit 4 tests. A later Maven log reported 9 tests, showing why a green build alone is not enough unless tests actually ran.

**Caution (run details verified; explanation unverified, 2026-10-07):** In pull request (PR) #2, the run without the script's Vintage insertion reported 9 tests with Maven Surefire (Maven's test-running plugin) 3.6.0; a later run with Surefire 3.5.4 reported 0. The runner images also differed.

The linked [runner-image release notes](https://github.com/actions/runner-images/releases/tag/ubuntu24/20261004.327) are reported to list Maven 3.9.16 on image `20260927.320.1` and 3.10.0 on image `20261004.327.1`; that page has not been independently reviewed. The linked [Surefire 3.6.0 guide](https://maven.apache.org/surefire-archives/surefire-LATEST/maven-surefire-plugin/whats-new-3-6-0.html) is reported to say that Surefire 3.6.0 can automatically provide Vintage support for JUnit 4; that guide has not been independently reviewed.

These differences could explain the run comparison, but they do not prove the cause: the logs do not print Maven's version or identify the exact engine loaded. The 3.5.4 run reported 0 tests, but that does not prove older Surefire versions always miss these tests.

The script's test-count pattern was also changed to `99999` before the later run, so that run does not prove the original zero-test guard works; Maven's zero-test result is separate evidence. Keep the Vintage insertion to make the build work across the observed plugin versions.

**Reading plugin versions in a Maven log:** A plugin line can look like `--- surefire:3.6.0:test (default-test) @ vprofile ---`; the number after the plugin name is the version used in that run. When comparing runs, check these plugin lines, the `Using auto detected provider` line (the test-running component Surefire selected), the `Tests run:` total, the runner image, and the submodule commit. PR #2's image and plugin versions differed; Run #8's script also had its test-count pattern changed to `99999`, which forced the later script error after Maven and did not cause Maven's zero-test result.

**How JUnit Vintage fits:** JUnit Vintage lets the JUnit 5 test system run JUnit 4 tests. The shared script adds this library to the temporary POM copy, checks Maven's test summary, and leaves the pinned source POM unchanged.

**Where a dependency goes:** XML is a text format that marks parts of a file with tags. `<dependencies>` starts the library list and `</dependencies>` ends it. Put a new `<dependency>...</dependency>` block just before the closing tag so Maven treats it as a library.

**Build script and temporary copy:** `scripts/build.sh` copies VProfile into `build-work/`, removes the copied Git metadata (the `.git` history and tracking data), edits only the copied `pom.xml`, runs Maven, and checks the test result and WAR. Copying first keeps the pinned `vprofile-src/pom.xml` unchanged; removing `.git` from the copy is separate cleanup.

**Finding the project folder:** `BASH_SOURCE[0]` is the path Bash used to start the script. `dirname` keeps its folder, `scripts/..` goes up to the repository, and `pwd` prints that full folder path for `ROOT`; this lets the script find its files even if it is started from another folder.

**Quoted paths:** Quotes around a path or variable keep spaces together as one path. The script quotes variables such as `"$WORK"` so shell commands do not split a folder path at its spaces.

**Safe cleanup and ignored output:** `rm -rf "$WORK"` removes the folder stored in `WORK`, so the script points `WORK` to the dedicated `build-work/` folder under the repository. `.gitignore` excludes `build-work/` so its temporary source copy, Maven log, and WAR are not mistaken for files to commit.

**Conditional checks:** `A && B` runs `B` only when `A` succeeds; `A || B` runs `B` only when `A` fails. The script uses these to stop with a clear message when a required file or POM section is missing, or when the Vintage dependency is already present.

**`grep -c` and `|| true`:** `grep -c` prints how many lines contain a match; if none match, it prints 0 but returns a failure status. The script adds `|| true` so `set -e` does not stop before the later check can print a clear error.

**`if grep -Fq`:** `-F` searches for exact text, and `-q` keeps the search quiet. The script uses `if` to check whether the POM already contains the Vintage dependency; the script can then stop with its own explanation if it finds it.

**Exit code and syntax check:** `$?` holds the result of the previous command; 0 means success. `bash -n scripts/build.sh` checks Bash syntax without running the script, so it cannot prove the Maven build works.

**POM edit with `sed`:** `sed` is a command-line text editor (short for stream editor). In `s#OLD#NEW#`, the command means “replace OLD with NEW”; `#` marks the boundaries, and it is used because the old text contains `/`. The command replaces every match, so the script checks that the POM has exactly one opening and one closing dependencies tag first.

The replacement must put `</dependencies>` back. Without it, the POM is invalid XML, even if `sed` itself succeeds; Maven reports the problem when it reads the file. Without `-i`, `sed` only prints the edited text and changes no file; with `-i`, it saves the edit into the file.

**Maven command:** In `mvn -B clean package`, `-B` selects batch mode, `clean` removes old build output, and `package` builds the app, runs configured tests, and creates the WAR. The script checks the Maven log for a positive test count because an earlier build succeeded while running zero tests.

**Output channels and redirection:** Bash labels its two output routes `1` and `2`. Route `1` is normally for regular output, and route `2` is normally for error output; both usually appear in the terminal. Redirection decides where they go.

`> out.txt` redirects route `1` to a file, so route `2` stays on screen. `2>&1` sends route `2` to the same place as route `1`; for example, `demo > out.txt 2>&1` sends both to the file.

**Failure settings:** In `set -euo pipefail`, `-e` stops the script after an unhandled command failure, `-u` treats an unset variable as an error, and `pipefail` makes a pipeline fail if any command in it fails. This lets a Maven failure in `mvn ... | tee mvn.log` reach `-e` even if `tee` succeeds.

**Pipe and tee:** `|` sends channel 1 from the command on its left to the command on its right; `tee mvn.log` writes received output to both the screen and `mvn.log`. In `mvn ... 2>&1 | tee mvn.log`, `2>&1` combines channel 2 with channel 1 before the pipe, so both can reach `tee`.

**Positive test-count pattern:** A regular expression (regex) is a text pattern used to find a match. In `[1-9][0-9]*`, the first digit must be 1–9, and `*` allows zero or more digits after it; `9` and `12` match, but `0` does not. The script uses this to reject `Tests run: 0`, but it checks for a positive test-result line rather than adding up every suite.

**Line endings:** LF (`\n`) is one character; CRLF (`\r\n`) is a carriage return (CR) followed by a line feed (LF). The pinned POM has 321 CRs and 321 LFs, so each line ends with CRLF. `git ls-files --eol` shows how Git stores a file (`i/`) and how the checked-out file is stored (`w/`). `i/lf w/crlf` means Git stores LF and the checked-out file uses CRLF.

**What the line-ending check showed:** `sed -i` changed the whole scratch copy and the whole `build-work/pom.xml` copy to LF. Direct byte counts found 0 CR and 321 LF in each copy; the pinned source still has 321 CR and 321 LF. The Maven log from the `build-work/` run shows that copy built successfully with 9 tests. This verifies that run on this machine; it does not verify other `sed` versions or platforms.

**Seeing line endings:** `cat -A` can show `$` at an LF line end and `^M$` at a CRLF line end; `od -c` displays the actual `\r` and `\n` characters. In the Git Bash (a Windows terminal with Bash and Git tools) check for this POM, `grep -c $'\r'` returned 0 even though `od` found 321 CR characters, so that grep result was not reliable for this file.

**Comparing files with different line endings:** If one file uses CRLF and another uses LF, `diff` may show every line as changed. The Git Bash `diff --strip-trailing-cr old-file new-file` command ignores the trailing CR so the output focuses on text changes.

**Cross-shell Git check (reported from Ubuntu WSL, 2026-10-17):** `git ls-files --eol` showed `i/lf w/crlf` for sampled repository files: Git's index used LF, while WSL's working files used CRLF. `git diff --ignore-cr-at-eol --stat` removed the apparent tracked-file changes and left only the separate `vprofile-src` submodule entry, so the other listed differences were line endings in that WSL view. The lowercase `m` in submodule status means content inside `vprofile-src` was modified; the 2026-10-18 checks in section 7 fit line-ending-only changes there too, but do not prove it. [Git status and submodule marks](https://git-scm.com/docs/git-status).

A later Git Bash status on the same day listed only `NOTES.md` and `PROGRESS.md` as modified, with `docs/` and `infra/bootstrap/backend.tf` untracked. The other tracked files listed as modified in WSL did not appear as modified in Git Bash, and `vprofile-src` showed no change. That status does not separate real edits from line-ending changes in the two listed files. `core.autocrlf` is Git's setting for converting line endings between the working copy and Git. In Git Bash, `git config --show-origin core.autocrlf` printed `true`, set in Git for Windows' system configuration. This fits the line-ending explanation. On 2026-10-18, `git config --show-origin core.autocrlf` printed nothing in Ubuntu WSL, so the setting is unset there (reported from terminal output). The difference between the shells fits, but changing the setting was not tested, so the cause is not confirmed.

## 3. Run the build checks automatically

**Continuous integration (CI)** means a computer automatically builds and checks code when a change happens. A pipeline is the list of steps that computer runs. A GitHub Actions **workflow** is the file that tells GitHub which steps to run and when. In this project, the pipeline lives in its own repository and gets the pinned VProfile version through the `vprofile-src` submodule.

The local Phase 1 workflow declares three events: `pull_request` checks a proposed change, `push` to `main` checks a commit after it is pushed, and `workflow_dispatch` starts a run by hand. The job builds and tests without AWS access. **Polling** checks for changes on a timer; a **webhook** sends a message when a change happens, such as after a push. A **required status check** is a passing job GitHub must see before it allows a change into `main`.

**Why Phase 1 has no AWS access:** Its job is only to build and test the source, so AWS credentials are not needed. Keeping them out also reduces the chance that pull-request code can reach cloud resources; the trade-off is that deployment needs a separate, protected workflow and its own permissions later.

Public-repo logs may be visible to other people. Not uploading an artifact (a saved file made by a build) does not hide text printed by `tee`; build output still appears in the workflow log. Never print VProfile source files, WAR contents, passwords, or keys in those logs. A GitHub-hosted runner, a temporary computer that runs the workflow, cannot directly connect to an EC2 (Elastic Compute Cloud) instance, an AWS virtual computer, in a private subnet (a network section without a direct route to the internet); deployment needs an AWS-managed path such as AWS Systems Manager (SSM).

Jenkins is planned for the next phase. Its **controller** organizes jobs; an **agent** computer runs their commands. A `Jenkinsfile` is a file of Jenkins job instructions; the instructor's file is not the design source for this project, so design the pipeline from the project needs. CI/CD means Continuous Integration and Continuous Delivery or Deployment: automatically build and check changes, then prepare or release them. The course also covers GitLab CI/CD, but the exact lecture order and instructor repo layout were not verified.

Project 3's infrastructure and playbooks are being designed from project requirements. Course provisioning scripts are not required and will not be inspected or copied; choose the target operating system (OS), the core software that runs a computer, from verified AWS, SSM, and package needs rather than script similarity.

**Runner and steps:** A runner is the temporary computer GitHub provides for a job; the hosted runner is removed when the job ends. In this workflow, checkout gets the repository and pinned submodule, setup-java installs Temurin 17 (a build of Java), and `run: bash scripts/build.sh` starts the build, so each run repeats the setup.

A **runner image** is the set of software installed on the hosted runner, such as Java and Maven. Its version appears under **Runner Image** in the Set up job log. GitHub updates images over time, so the same workflow can use different software versions on different runs; the separate **Hosted Compute Agent** block describes GitHub's runner service, not the image (verified from PR #2 logs).

**Actions, commands, and names:** A step with `uses:` runs a packaged action; this workflow uses checkout and setup-java actions from other repositories, while `run:` executes a shell command. Step names label log sections, but the workflow name feeds `github.workflow` in the concurrency group and the job name identifies the status check, so changing those names can affect cancellation grouping or required-check matching.

**SHA pinning:** SHA is short for Secure Hash Algorithm; a commit SHA is the fingerprint Git uses to identify one exact saved version. Pinning an action to its SHA selects that exact version, while a version tag is a name its owners can move. This workflow pins checkout and setup-java by SHA, so using a newer action version requires changing the pinned SHA.

**Token and permissions:** A credential is a secret, such as a password or token, used to prove identity or access. GitHub gives each workflow run a `GITHUB_TOKEN`, a temporary credential used to access GitHub, and `permissions` limits what it can do. `contents: read` allows the workflow to read repository contents without permission to push changes; `persist-credentials: false` tells checkout not to save the token as a Git credential in the repository's local configuration.

**Concurrency groups:** This workflow builds a group from `github.workflow` (the workflow's name) and `github.ref` (the branch or other Git reference for the run). With `cancel-in-progress: true`, a new run cancels an older run only when they share a group and the older run is still running; two runs on `main` share a group, while a pull request uses a different ref.

**Three triggers (verified 2026-10-07):** `push` runs after a commit lands on `main`, `workflow_dispatch` runs when you click "Run workflow" by hand, and `pull_request` runs on a proposed change before it merges. In this project, run #4 was manual (40 s), and PR #1's check passed (28 s).

**Pull request (PR):** A PR asks GitHub to merge one branch into another, such as `docs/record-phase1-checks` into `main`. GitHub tests a temporary merge of the two; the PR #2 log shows `refs/remotes/pull/2/merge`. A PR is how a change reaches `main` now.

**Ruleset and required check (reported verified 2026-10-07; not rechecked since):** A ruleset is a set of rules GitHub applies to chosen branches. At that checkpoint, `protect-main` was active on `main`, required `build-test` from GitHub Actions, and blocked force pushes. On PR #2, the failing check carried a Required badge and the Merge button was disabled. A direct push to `main` was expected to be refused, but was not tested.

**Why test a failure path:** A pipeline that has only passed has not shown it can fail. In PR #2, the count pattern was changed to `99999`, so the job ended with `ERROR: Maven did not report any tests as run.` and exit code 1, even though Maven said `BUILD SUCCESS`. This shows the script's error path works. It does not show the original check rejects 0 tests, because `99999` fails for any count.

**Token permissions (verified):** The Set up job log listed only `Contents: read` and `Metadata: read`, so the workflow cannot push changes to the repository.

**Checkout credential cleanup (verified):** With `persist-credentials: false`, checkout stores a temporary credential file outside the repository and adds `includeIf` pointers to it in the repo's config. After the checkout, it removes the pointers and logs `Removing credentials config`. The hosted runner is deleted when the job ends.

**Apps that add checks (verified access, reported origin):** A GitHub App with "All repositories" access can add its own check and comment to a PR without appearing in the workflow file. SonarQubeCloud did this on PRs #1 and #2. Its Udemy-course origin is reported but not independently verified. It is not part of Project 3's scope.

## 4. Save and deliver the built app

The WAR is the packaged web app file made by the build. **Nexus** stores versioned build files; it does not build or run the app. **Amazon S3 (Simple Storage Service)** is AWS storage for files and other data. For example, a private artifact store could keep the VProfile WAR made by a successful build. **SonarQube** checks code quality. Nexus remains undecided, while SonarQube Cloud is an external PR check rather than an approved Project 3 quality gate. Neither tool is in the approved scope; adding either requires later approval.

A build number plus the source commit can identify which run made a WAR and which app version it used. A health check can see whether the deployed app responds. A rollback can return to an earlier version if the new one fails. These are planned behaviors, not completed or tested features.

The WAR must stay private. Do not put it in a public repo, release, or log. The source-use permission is unresolved, so attribution must stay and public sharing of the built WAR is not allowed unless permission is established. Under the current project instructions, a private-only copy (for example, in private S3) is an accepted risk, not permission, and still needs the design, cost, and implementation approvals.

**Private S3 and retention (prior-account D1; role access was still planned at that checkpoint):** S3 Block Public Access blocks public access; encryption protects stored data but does not decide which role can read it. Prior-account D1 created the WAR and transfer buckets with Block Public Access, S3-managed default encryption, and HTTPS-only policies; the WAR expires after 30 days and Ansible transfer files after 1 day. At that checkpoint, GitHub upload and Ansible transfer permissions were not implemented. These read-backs do not establish settings for the new account. Its review uses runner-side S3 permissions and presigned URLs; it does not plan standing instance S3 IAM access for the documented transfer path. The selected plugin version/configuration and actual transfer remain unverified.

**Why keep three separate buckets until project close (prior-account D1; new-account buckets reported created):** The state bucket keeps Terraform's record, the WAR bucket is for build files, and the Ansible bucket is for short-lived helper files. In the prior account, bootstrap created the state bucket and D1 added the WAR and transfer buckets. In the new account, author-supplied output reports the state, WAR, and transfer buckets created. Keeping durable buckets outside the per-session stack means destroying that stack can leave them in place, but they need separately approved cleanup and must be empty before deletion. Account alignment remains reported by the author, not independently verifiable in this record.

**Versioning, overwrite, and expiry (prior-account D1 choices; S3 behavior reported, not independently checked):** An S3 key is a file's name in the bucket. Without versioning, uploading to an existing key replaces the old file, and deleting a file removes it for good. For example, if CI uploaded a different file to `vprofile-v2-build42-9f22748.war`, the build 42 WAR would be gone. Unique keys make that unlikely but do not prevent it. A lifecycle rule that expires by age fits unique keys; "keep the last N builds" does not, because S3 counts versions of one key, not different keys. Expiry is a cleanup, not an exact timer. In a versioned bucket, expiry adds a delete marker (a record that makes the object look deleted while older versions remain), and old versions need their own rule. The new-account Terraform state bucket is recorded as versioned with a 30-day rule for old versions. Prior-account D1 WAR and Ansible buckets were not versioned; those settings do not establish the new-account transfer bucket's setting. The earlier new-account CLI read returned no status, while a later author-supplied Properties screenshot reports `Disabled` for the named transfer bucket; see the [new-account design decision](docs/decisions/new-account-deployment-design.md#2026-10-23-ansible-transfer-bucket-stays-unversioned-planning-only).

**Health check (planned):** A health check asks whether the deployed VProfile app is ready to serve requests. The port, real app URL (web address), and response that proves the app is healthy are undecided; Tomcat, the Java web server, on port `8080` is only a candidate from memory.

HTTP (Hypertext Transfer Protocol) is a set of rules computers use to send web requests and responses. A `200` response means the request succeeded, but it may not prove the VProfile page or its dependencies are working. The check should retry while Tomcat starts and require text that only the VProfile page contains, because another program could also return `200`.

The expected text should be chosen after seeing the real response. A login-page response alone does not prove that MySQL (database software that stores app records), Memcached (a service that stores recent data in memory for quick reads), or RabbitMQ (a service that passes messages between programs) are working. The check's result must determine whether deployment succeeded.

Manual SSM port forwarding is for viewing the private app. An earlier proposal put the automated check on the instance through SSM Run Command because a GitHub-hosted runner cannot directly reach the private instance. The 2026-10-23 working design instead uses Ansible’s `aws_ssm` connection from the runner; the exact automated health-check mechanism remains undecided, and deploy permission policy v1 does not include `ssm:SendCommand`.

**Finding the app's address (partly reported; not tested, 2026-10-11):** Tomcat normally uses a WAR's file name as the web address path: `vprofile-v2.war` would likely be at `/vprofile-v2/`, while `ROOT.war` would use `/` (general convention, not tested here). The `/` page is reported to show a login screen; a response from it alone does not prove that MySQL, Memcached, or RabbitMQ are working. The `/users` page is reported to list users' names and IDs, so it is not used as a health check.

**Rollback (planned; not built or tested):** A rollback puts the previous working WAR back if a new one fails its health check. For example, if build 42 never passes, the deployment document would download the build 41 WAR from S3, put it back in Tomcat, and run the same health check again. This needs unique S3 keys so an earlier WAR is not overwritten, a record of which build is working (where it lives is undecided), and a final result that turns the workflow red even when rollback succeeds. Rollback replaces only the WAR: it does not undo database changes, cannot work if retention has deleted every earlier WAR, and the first deployment has nothing to return to. Demonstrating it needs a deliberately failing deployment, which needs separate approval.

**Security rules and the filter (code reading; not tested, 2026-10-11):** A filter is code that checks every web request before the app answers it. `appconfig-security.xml` says `/` needs a logged-in user, but that rule works only if a filter loads it. A search under `src/main` found no filter registration, so the rules may not apply; only a running app shows which is true.

## 5. Add AWS resources only after the design and cost gate

**Terraform** is planned to create cloud resources such as networks, computers, and permissions from configuration files. **Ansible** is planned to install software and set up computers and apps. See **Terraform state, backend, and locking** below for the proposed remote S3 state, encryption, versioning, and lock settings.

An AWS **IAM (Identity and Access Management) role** is an AWS identity that gives a computer limited permissions. For example, a build computer should get only the AWS access it needs. Jenkins credentials are stored passwords or tokens used by tools. Do not commit passwords or keys. AWS Secrets Manager is a managed AWS service for storing and retrieving sensitive values such as passwords and keys.

**SSM access (planned):** SSM means AWS Systems Manager. Session Manager lets a person open a shell or forward a port to an EC2 instance. The SSM Agent starts outbound connections (from the instance to AWS), so Session Manager does not need inbound connections (new connections coming from outside toward the instance) or SSH (Secure Shell, a way to open a remote command session). It does not give the instance general internet access. The planned choice favors managed access without opening SSH; the trade-off is that the agent, IAM permissions, and a working network path must all be present.

**Port forwarding (planned):** A port is a number that directs a connection to a program, such as Tomcat. The SSM Agent is a background program on the instance that connects it to Systems Manager. SSM port forwarding connects a local port to the instance through the Agent's outbound session, so it needs no inbound connection. In `http://localhost:8080`, `localhost` means this computer, and the request is forwarded to the chosen Tomcat port on the instance. The forwarded connection works only while the local command is running. `8080` is an example only; the target port still needs confirmation.

**Private network and updates (planned design):** A network connects computers so they can send data. A subnet is a smaller part of a network, and a VPC (Virtual Private Cloud) is a private network in AWS. A route tells network traffic where to go. A public subnet has a route to an internet gateway (an AWS connection from a VPC to the internet); a private subnet does not route directly to that gateway.

NAT (Network Address Translation) lets a private computer start internet connections without its own public address. The planned private subnet plus NAT lets the instance reach SSM and software-download sites without a public IP. Compared with the cheaper public-subnet fallback, NAT adds hourly and data-processing costs; compared with SSM interface endpoints, it can reach more software sites.

If NAT is the only outbound path, deleting it while keeping the instance stops SSM and package access. The per-session destroy-and-rebuild plan avoids leaving an unreachable instance; regional NAT prices and data use must be checked before implementation.

**NAT Gateway cost model (planning estimate):** A NAT Gateway has an hourly charge and a per-GB data-processing charge; internet data transfer may add another cost. The project estimate uses reported example rates of $0.045 per gateway-hour and $0.045 per GB, not a verified current N. Virginia quote. Check the AWS Pricing Calculator for the selected Region before billable implementation. [VPC pricing](https://aws.amazon.com/vpc/pricing/), [EC2 cost formula](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-instance-addressing.html), [2023 us-east-1 example](https://aws.amazon.com/blogs/networking-and-content-delivery/identify-and-optimize-public-ipv4-address-usage-on-aws/).

**Public-IP fallback (planned):** A public IPv4 address and route to an internet gateway let an instance start outbound connections. A security group is an AWS network filter for an instance; with no inbound rules it blocks new incoming connections to the instance, but the public address makes accidental inbound-rule changes a larger risk and departs from the private-subnet design.

**Package setup:** SSM interface endpoints provide a private path from the VPC to SSM, but not to arbitrary package sites. An S3 gateway endpoint routes a VPC's traffic to S3 without NAT and has no hourly endpoint charge; it does not reach package sites. A prepared Amazon Machine Image (AMI), a saved disk image for starting an EC2 computer, can include software before an instance starts, but it must be rebuilt to receive later package and security updates.

The current review-only design uses a `production` Environment restricted to `main`, and the trust draft checks repository identity plus branch and environment claims. **Temporary credentials and logs (planned):** Temporary AWS credentials stop working at expiry, which limits how long a leaked value can be used. They remain sensitive while valid, so never print them in a public workflow log.

**Long-lived and temporary credentials:** An AWS access key does not expire automatically. A CLI profile can use an access key stored in plaintext in `~/.aws/credentials` to request a temporary role session with MFA, so restrict the file permissions and remove the key when it is no longer needed. The role's permissions control actions in that session, but they do not make the source key temporary; deactivation is reversible, while deletion is not, so check dependencies first.

**Trust and permissions policies:** A role's trust policy names who may assume it and can require conditions such as MFA; its permissions policy controls AWS actions after assumption. AWS says a same-account trust policy that names an IAM user can allow that user to assume the role without an identity-policy `Allow`. AWS combines same-account identity-based and resource-based `Allow` permissions, while an explicit `Deny` overrides them. Therefore, the reported `p3-cli` policy that allows `sts:AssumeRole` on `p3-terraform` is not by itself a hard deny against another role whose trust policy directly names `p3-cli`. Any future role, such as Project 5's, must not name p3-cli in its trust policy unless that key should be able to reach it. [AWS STS AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html), [AWS IAM policy evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html). **HTTPS-only policy (applied and verified 2026-10-17; AWS guidance reported, not independently opened):** HTTPS is a web connection protected with encryption while it travels; HTTP does not provide that transport protection. SSE-S3 means server-side encryption with S3-managed keys and protects stored objects. A bucket policy is a rule attached to a bucket that controls requests, and its `Deny` for `aws:SecureTransport=false` makes S3 reject HTTP requests. The policy was applied to the state bucket, and a live `get-bucket-policy` read-back showed the `DenyInsecureTransport` rule; `terraform plan` then reported no changes. Denial of a real plain-HTTP request was not tested. Terraform and the AWS CLI already use HTTPS, so the policy mainly guards against a misconfigured client. It does not protect local copies of the state file.

This policy names both the bucket ARN (Amazon Resource Name, AWS's full resource name) and its `/*` object ARN, so it covers matching bucket-level and object requests. A client-side HTTPS convention only governs that client; the bucket policy applies to requests from any caller that match the deny condition. AWS warns that some service-to-service calls may not include transport details in the policy context. A future AWS service integration may therefore need an exception such as `aws:PrincipalIsAWSService=false` in the deny condition.

**Interview explanation:** “The bucket policy denies HTTP requests to the bucket and its objects when they match the deny condition. HTTPS protects data while it travels; SSE-S3 protects stored objects. We verified the stored policy with `get-bucket-policy`, but did not test a plain-HTTP request. The trade-off is another managed policy and its IAM lifecycle permissions, with possible exceptions for future AWS service integrations.” [AWS transport-security guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryptionInTransit.html), [AWS condition-key guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html).

**Bucket ARN versus object ARN:** An ARN is AWS's full resource name. The bucket ARN, such as `arn:aws:s3:::p3-vprofile-tfstate-x4b8t3`, names the bucket itself; adding `/` and an object key names one object inside it, for example `arn:aws:s3:::p3-vprofile-tfstate-x4b8t3/bootstrap/terraform.tfstate`. A policy must match both the action and the resource: `s3:ListBucket` applies to the bucket ARN, while `s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject` apply to object ARNs. A bucket-level permission therefore does not grant permission to read or save a state file. `infra/bootstrap/backend.tf` names `bootstrap/terraform.tfstate`, and the migration placed the state object at that key. [HashiCorp S3 backend permissions](https://developer.hashicorp.com/terraform/language/backend/s3), [AWS S3 actions and resources](https://docs.aws.amazon.com/service-authorization/latest/reference/list_s3.html).

**Reading the Job 1 state-bucket policy (2026-10-16):** `Sid` is an optional label for people reading the policy; it does not change access. `Version` selects the policy language, not an expiry date; `Effect` says allow or deny, `Action` names an AWS operation, and `Resource` names the target bucket by its full AWS resource name (ARN).

**Why the policy names exact actions and one bucket:** The design lists the S3 operations Terraform needs instead of granting `AdministratorAccess` or every S3 action (`s3:*`), and names only `p3-vprofile-tfstate-x4b8t3`. **Why bucket deletion is denied:** An explicit `Deny` for `s3:DeleteBucket` wins over an `Allow` for that action, so Terraform cannot remove the state bucket during ordinary stack cleanup. This keeps the bucket that stores Terraform's record beyond a session's destroy, but project-close deletion needs a separate approved step. The deny protects the bucket from deletion only; it does not protect its settings or the objects inside it.

**GitHub OIDC trust:** OpenID Connect (OIDC) lets a workflow prove its identity to AWS with a short-lived signed token instead of a long-lived AWS key stored in GitHub. The role trust policy decides who may assume the role; its permissions policy decides what the role may do. `aud` (audience) says the token is meant for AWS STS, and `sub` (subject) identifies the repository and branch.

**Earlier branch-only OIDC subject draft (historical; superseded for the new account):** That draft used exact `StringEquals` conditions on `aud=sts.amazonaws.com` and a `main` branch `sub`. [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).

**D2 OIDC provider notes:** The provider uses `https://token.actions.githubusercontent.com` as its issuer and `sts.amazonaws.com` as its allowed audience. The issuer is the identity provider that creates the token; a thumbprint is a certificate fingerprint AWS can use when validating that provider. The provider accepts tokens from that issuer and audience; the role's trust policy separately constrains workflow claims. The earlier Phase D draft used a branch subject; the new-account workflow later reported the `production` Environment subject. **Permissions boundaries (policy-draft mechanics):** A permissions boundary sets the maximum actions an identity policy may grant; it does not grant actions by itself. ## 6. Check AWS costs and live resources carefully

Stopping an EC2 computer stops its compute use, but storage and other resources can still cost money. A VPC is an AWS private network; the VPC itself has no hourly charge, while some resources in it can. An Application Load Balancer has its own billing line. Interface VPC endpoints can charge by the hour even when idle; S3 gateway endpoints have no endpoint-hour charge. Check current prices before making a cost decision.

Bills can update late. Cleaning up stops later use but does not remove earlier charges. A bill can show a charge and a separate credit that subtracts from it, so a zero total does not mean there was no usage. Cost Explorer can group charges by usage type. A service line alone may not prove which resource caused it.

**Credit-use rule (author direction, 2026-10-21):** The author accepts eligible usage consuming credits, excludes Organization changes and Control Tower landing zones as a precaution, and does not require routine CloudShell rechecks after ordinary actions. The AWS source details and the uncertainty for an already-Paid account are summarized below; a displayed balance alone does not show which charges qualify. [AWS Free Tier](https://aws.amazon.com/free/), [AWS Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/).

**Free-plan upgrade triggers (official AWS pages reviewed, 2026-10-21):** AWS lists these automatic upgrades from Free to Paid: joining AWS Organizations, setting up an AWS Control Tower landing zone, joining the AWS Partner Network, creating a Professional Services contract, enrolling in an Enterprise Agreement, purchasing an AWS Skill Builder Team subscription, and designating the account as HIPAA- or SEC-compliant. [Choosing an AWS plan](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans.html).

**Credit effects:** AWS's IAM Identity Center guide says creating an Organization upgrades a Free-plan account and immediately expires its credits. The current FAQ text reviewed separately says Organizations and Control Tower end activities and stop additional credit earning, but does not state that Control Tower immediately expires already-issued credits; older FAQ text reportedly does, so the sources differ. The FAQ says an ordinary Paid-plan upgrade leaves remaining credits available until expiry; activating advanced features also preserves earned credits until expiry but stops additional activity-credit earning. [AWS Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/), [AWS IAM Identity Center guide](https://docs.aws.amazon.com/singlesignon/latest/userguide/enable-identity-center.html).

**AWS Free Tier FAQ and Terms recheck (2026-10-22):** The live FAQ has separate passages about existing credits and earning activities. ## 7. Read command results before trusting them

`terraform state list` shows resources recorded in the selected Terraform state. `terraform plan -destroy` refreshes the state and previews what Terraform would remove; it does not remove anything. Compare that list with live AWS resources because something created outside Terraform may be missing from the state.

## OIDC trust, permissions boundaries, and the aws_ssm connection (learning notes, updated 2026-10-24)

### What a role's trust policy checks

A role has two separate policies. The permission policy says what the role may do. The trust policy says who may become the role. For GitHub OIDC, AWS compares fields in the workflow's signed token (called claims) with conditions in the trust policy. The applied deploy-role code uses exact `StringEquals` matching for `aud` (audience) and `sub` (subject), according to the local file and reported trust read-back. Earlier drafts also included `ref`, `environment`, `repository_id` and `repository_owner_id`; those conditions were removed by the author's 2026-10-24 planning choice. The author-supplied read-back reports the role trust saved, but GitHub has not assumed the role. See the [design decision](docs/decisions/new-account-deployment-design.md) for current evidence limits.

### Subject formats

- A branch run: the repository prefix, then `:ref:refs/heads/BRANCH`.
- A pull-request run: the repository prefix, then `:pull_request`.
- A job that uses a GitHub Environment: the repository prefix, then `:environment:NAME`. This form names the environment and not the branch, so a separate `ref` condition or an Environment branch rule is needed to keep the role to `main`.
- In the reported 2026-10-24 Run #1, a temporary workflow using `production` printed `repo:dmncfrncsc@104504982/cicd-pipeline-vprofile@1399501719:environment:production`. A second run from a non-main branch was blocked once by Environment protection rules. The author chose to rely on that GitHub rule rather than add a `ref` condition to AWS trust; administrator bypass remained enabled, so administrators can bypass the GitHub-side branch rule. The checker requested audience `sts.amazonaws.com`, but printed only `sub`; the `aud` claim was not separately displayed.
- For repositories created or renamed after 2026-07-15 (and repositories that opt in), the prefix includes the owner ID and repository ID joined with `@`. The repository's Actions settings, under OIDC, shows the exact prefix. A trust policy written with names only will not match.
- Use exact matching (`StringEquals`). GitHub's own AWS guide shows a wildcard example that also matches pull-request runs.

### A permissions boundary limits permissions, not trust

A boundary caps what a role can ever do, but it does not limit who can be named in the role's trust policy. A principal that can update a role's trust, or delete and recreate the role, can change who may assume it. An explicit Deny overrides any Allow, so a Deny on `iam:UpdateAssumeRolePolicy` and `iam:DeleteRole` closes both paths, provided the policy holding the Deny cannot be edited by the same principal. An MFA challenge controls credential issuance; it does not restrict actions in an issued session. Terraform plan review is procedural and does not block direct API calls. These are explanations of the draft and general IAM behavior, not results of a live permission test.
