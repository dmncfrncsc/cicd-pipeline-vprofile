# NOTES.md — `cicd-pipeline-vprofile` (Project 3)

These notes explain the project in the order its parts fit together and define technical terms with project examples. They preserve the reasoning needed for an end-to-end explanation: what was done and in what order, why important tools and methods were chosen over alternatives, the trade-offs, evidence, and limits. Check `PROGRESS.md` for current status and the next step.

## Project map — how the parts fit

Project 3 uses the instructor-provided VProfile sample web app to practice an automated build and delivery flow. Git records saved versions of files, and AWS (Amazon Web Services) provides computers, storage, and other services over the internet.

In Phase 1, GitHub Actions (GitHub's tool for running automated jobs) gets the pinned source, runs the shared build script with Maven (a Java build tool), and reports pass or fail; this phase has no AWS access. Jenkins (a server for running build and deployment jobs) and AWS deployment come later, after separate design and cost approval.

## 1. Choose the exact app code

**Source code** is the set of files that make the app. A **Git commit** is a saved snapshot of those files; its commit ID identifies that exact snapshot.

A **branch** is a movable name for a commit; new commits can move the name forward. A **repository** (repo) is a project folder Git tracks with its saved history.

A **fork** is your own copy of someone else's Git repo. A **submodule** links to another Git repo and records which exact commit this repo uses.

**In this project:** the Project 3 repo points to VProfile source through `vprofile-src`. Pinning a commit means each build can use the same app version. Changing the pointer selects a different version.

A submodule stores an exact commit ID, not a branch name. `git ls-remote` lists references advertised by the remote, so not seeing a commit ID there does not prove that the commit cannot be fetched; a commit that no retained reference points to may later become unavailable.

Different VProfile branches may use different Java versions. Java is the programming language used by this app. Earlier read-only checks identified `origin/local` and `origin/atom` as Java 17 WAR candidates, and `main` and `ci-jenkins` as Java 8 candidates. A branch name does not prove the app builds; inspect its files and build it before choosing. A Git reference (ref) is a name, such as a branch or tag, that points to a commit.

The VProfile app was made by the instructor, not by the author of Project 3. Earlier checks found no license file on `atom` or `origin/local`, and no license text in `README.md` or `pom.xml`. Missing license text does not grant permission. Keep attribution and do not share a built WAR publicly unless permission is established.

**Useful checks:** `pwd` shows the current folder. `git rev-parse --show-toplevel` prints the Git repository root. `git submodule status` shows the submodule commit. `git ls-tree -r --name-only <ref>` lists tracked file names at a commit without switching to it. A Git remote is the saved address of another copy of the repo; `git -C <repo> remote get-url origin` shows that address. A search only tells you about the folders it searched.

## 2. Build the app and make sure its tests run

**Maven and its POM:** Maven is a tool that builds Java apps. POM means Project Object Model; `pom.xml` lists build settings and dependencies (libraries the app uses). The instructor supplied VProfile and its POM; developers normally maintain the POM for an app they own. In this project, the script edits the copied POM in `build-work/`, not the pinned file in `vprofile-src/`; Maven packages the app as a **WAR** (Web Application Archive, a packaged web app file).

**Why test count matters:** An earlier Maven run reported `BUILD SUCCESS` but ran 0 tests because the app's tests use JUnit 4, a Java testing tool, while Maven had only the JUnit 5 test engine (the part that finds and runs tests; see the caution below). JUnit Vintage lets the JUnit 5 test system run JUnit 4 tests. A later Maven log reported 9 tests, showing why a green build alone is not enough unless tests actually ran.

**Caution (run details verified; explanation unverified, 2026-10-07):** In pull request (PR) #2, the run without the script's Vintage insertion reported 9 tests with Maven Surefire (Maven's test-running plugin) 3.6.0; a later run with Surefire 3.5.4 reported 0. The runner images also differed.

The linked [runner-image release notes](https://github.com/actions/runner-images/releases/tag/ubuntu24/20261004.327) are reported to list Maven 3.9.16 on image `20260927.320.1` and 3.10.0 on image `20261004.327.1`; that page has not been independently reviewed. The linked [Surefire 3.6.0 guide](https://maven.apache.org/surefire-archives/surefire-LATEST/maven-surefire-plugin/whats-new-3-6-0.html) is reported to say that Surefire 3.6.0 can automatically provide Vintage support for JUnit 4; that guide has not been independently reviewed.

These differences could explain the run comparison, but they do not prove the cause: the logs do not print Maven's version or identify the exact engine loaded. The 3.5.4 run reported 0 tests, but that does not prove older Surefire versions always miss these tests.

The script's test-count pattern was also changed to `99999` before the later run, so that run does not prove the original zero-test guard works; Maven's zero-test result is separate evidence. Keep the Vintage insertion to make the build work across the observed plugin versions.

**Reading plugin versions in a Maven log:** A plugin line can look like `--- surefire:3.6.0:test (default-test) @ vprofile ---`; the number after the plugin name is the version used in that run. When comparing runs, check these plugin lines, the `Using auto detected provider` line (the test-running component Surefire selected), the `Tests run:` total, the runner image, and the submodule commit. PR #2's image and plugin versions differed; Run #8's script also had its test-count pattern changed to `99999`, which forced the later script error after Maven and did not cause Maven's zero-test result.

**How JUnit Vintage fits:** JUnit Vintage lets the JUnit 5 test system run JUnit 4 tests. The shared script adds this library to the temporary POM copy, checks Maven's test summary, and leaves the pinned source POM unchanged.

**Where a dependency goes:** XML is a text format that marks parts of a file with tags. `<dependencies>` starts the library list and `</dependencies>` ends it. Put a new `<dependency>...</dependency>` block just before the closing tag so Maven treats it as a library.

**Build script and temporary copy:** `scripts/build.sh` copies VProfile into `build-work/`, removes the copied Git metadata (the `.git` history and tracking data), edits only the copied `pom.xml`, runs Maven, and checks the test result and WAR. Copying first keeps the pinned `vprofile-src/pom.xml` unchanged; removing `.git` from the copy is separate cleanup.

**Finding the project folder:** `BASH_SOURCE[0]` is the path Bash used to start the script. `dirname` keeps its folder, `scripts/..` goes up to the repository, and `pwd` prints that full folder path for `ROOT`; this lets the script find its files even if it is started from another folder.

**Quoted paths:** Quotes around a path or variable keep spaces together as one path. The script quotes variables such as `"$WORK"` so shell commands do not split a folder path at its spaces.

**Safe cleanup and ignored output:** `rm -rf "$WORK"` removes the folder stored in `WORK`, so the script points `WORK` to the dedicated `build-work/` folder under the repository. `.gitignore` excludes `build-work/` so its temporary source copy, Maven log, and WAR are not mistaken for files to commit.

**Conditional checks:** `A && B` runs `B` only when `A` succeeds; `A || B` runs `B` only when `A` fails. The script uses these to stop with a clear message when a required file or POM section is missing, or when the Vintage dependency is already present.

**`grep -c` and `|| true`:** `grep -c` prints how many lines contain a match; if none match, it prints 0 but returns a failure status. The script adds `|| true` so `set -e` does not stop before the later check can print a clear error.

**`if grep -Fq`:** `-F` searches for exact text, and `-q` keeps the search quiet. The script uses `if` to check whether the POM already contains the Vintage dependency; the script can then stop with its own explanation if it finds it.

**Exit code and syntax check:** `$?` holds the result of the previous command; 0 means success. `bash -n scripts/build.sh` checks Bash syntax without running the script, so it cannot prove the Maven build works.

**POM edit with `sed`:** `sed` is a command-line text editor (short for stream editor). In `s#OLD#NEW#`, the command means “replace OLD with NEW”; `#` marks the boundaries, and it is used because the old text contains `/`. The command replaces every match, so the script checks that the POM has exactly one opening and one closing dependencies tag first.

The replacement must put `</dependencies>` back. Without it, the POM is invalid XML, even if `sed` itself succeeds; Maven reports the problem when it reads the file. Without `-i`, `sed` only prints the edited text and changes no file; with `-i`, it saves the edit into the file.

**Maven command:** In `mvn -B clean package`, `-B` selects batch mode, `clean` removes old build output, and `package` builds the app, runs configured tests, and creates the WAR. The script checks the Maven log for a positive test count because an earlier build succeeded while running zero tests.

**Output channels and redirection:** Bash labels its two output routes `1` and `2`. Route `1` is normally for regular output, and route `2` is normally for error output; both usually appear in the terminal. Redirection decides where they go.

`> out.txt` redirects route `1` to a file, so route `2` stays on screen. `2>&1` sends route `2` to the same place as route `1`; for example, `demo > out.txt 2>&1` sends both to the file.

**Failure settings:** In `set -euo pipefail`, `-e` stops the script after an unhandled command failure, `-u` treats an unset variable as an error, and `pipefail` makes a pipeline fail if any command in it fails. This lets a Maven failure in `mvn ... | tee mvn.log` reach `-e` even if `tee` succeeds.

**Pipe and tee:** `|` sends channel 1 from the command on its left to the command on its right; `tee mvn.log` writes received output to both the screen and `mvn.log`. In `mvn ... 2>&1 | tee mvn.log`, `2>&1` combines channel 2 with channel 1 before the pipe, so both can reach `tee`.

**Positive test-count pattern:** A regular expression (regex) is a text pattern used to find a match. In `[1-9][0-9]*`, the first digit must be 1–9, and `*` allows zero or more digits after it; `9` and `12` match, but `0` does not. The script uses this to reject `Tests run: 0`, but it checks for a positive test-result line rather than adding up every suite.

**Line endings:** LF (`\n`) is one character; CRLF (`\r\n`) is a carriage return (CR) followed by a line feed (LF). The pinned POM has 321 CRs and 321 LFs, so each line ends with CRLF. `git ls-files --eol` shows how Git stores a file (`i/`) and how the checked-out file is stored (`w/`). `i/lf w/crlf` means Git stores LF and the checked-out file uses CRLF.

**What the line-ending check showed:** `sed -i` changed the whole scratch copy and the whole `build-work/pom.xml` copy to LF. Direct byte counts found 0 CR and 321 LF in each copy; the pinned source still has 321 CR and 321 LF. The Maven log from the `build-work/` run shows that copy built successfully with 9 tests. This verifies that run on this machine; it does not verify other `sed` versions or platforms.

**Seeing line endings:** `cat -A` can show `$` at an LF line end and `^M$` at a CRLF line end; `od -c` displays the actual `\r` and `\n` characters. In the Git Bash (a Windows terminal with Bash and Git tools) check for this POM, `grep -c $'\r'` returned 0 even though `od` found 321 CR characters, so that grep result was not reliable for this file.

**Comparing files with different line endings:** If one file uses CRLF and another uses LF, `diff` may show every line as changed. The Git Bash `diff --strip-trailing-cr old-file new-file` command ignores the trailing CR so the output focuses on text changes.

**Cross-shell Git check (reported from Ubuntu WSL, 2026-10-17):** `git ls-files --eol` showed `i/lf w/crlf` for sampled repository files: Git's index used LF, while WSL's working files used CRLF. `git diff --ignore-cr-at-eol --stat` removed the apparent tracked-file changes and left only the separate `vprofile-src` submodule entry, so the other listed differences were line endings in that WSL view. The lowercase `m` in submodule status means content inside `vprofile-src` was modified; the 2026-10-18 checks in section 7 fit line-ending-only changes there too, but do not prove it. [Git status and submodule marks](https://git-scm.com/docs/git-status).

A later Git Bash status on the same day listed only `NOTES.md` and `PROGRESS.md` as modified, with `docs/` and `infra/bootstrap/backend.tf` untracked. The other tracked files listed as modified in WSL did not appear as modified in Git Bash, and `vprofile-src` showed no change. That status does not separate real edits from line-ending changes in the two listed files. `core.autocrlf` is Git's setting for converting line endings between the working copy and Git. In Git Bash, `git config --show-origin core.autocrlf` printed `true`, set in Git for Windows' system configuration. This fits the line-ending explanation. On 2026-10-18, `git config --show-origin core.autocrlf` printed nothing in Ubuntu WSL, so the setting is unset there (reported from terminal output). The difference between the shells fits, but changing the setting was not tested, so the cause is not confirmed.

## 3. Run the build checks automatically

**Continuous integration (CI)** means a computer automatically builds and checks code when a change happens. A pipeline is the list of steps that computer runs. A GitHub Actions **workflow** is the file that tells GitHub which steps to run and when. In this project, the pipeline lives in its own repository and gets the pinned VProfile version through the `vprofile-src` submodule.

The Phase 1 workflow is configured for three events: `pull_request` checks a proposed change, `push` to `main` checks a commit after it is pushed, and `workflow_dispatch` starts a run by hand. The job builds and tests without AWS access. **Polling** checks for changes on a timer; a **webhook** sends a message when a change happens, such as after a push. A **required status check** is a passing job GitHub must see before it allows a change into `main`; the ruleset `protect-main` now requires `build-test` (verified 2026-10-07).

**Why Phase 1 has no AWS access:** Its job is only to build and test the source, so AWS credentials are not needed. Keeping them out also reduces the chance that pull-request code can reach cloud resources; the trade-off is that deployment needs a separate, protected workflow and its own permissions later.

Public-repo logs may be visible to other people. Not uploading an artifact (a saved file made by a build) does not hide text printed by `tee`; build output still appears in the workflow log. Never print VProfile source files, WAR contents, passwords, or keys in those logs. A GitHub-hosted runner, a temporary computer that runs the workflow, cannot directly connect to an EC2 (Elastic Compute Cloud) instance, an AWS virtual computer, in a private subnet (a network section without a direct route to the internet); deployment needs an AWS-managed path such as AWS Systems Manager (SSM).

Jenkins is planned for the next phase. Its **controller** organizes jobs; an **agent** computer runs their commands. A `Jenkinsfile` is a file of Jenkins job instructions; the instructor's file is not the design source for this project, so design the pipeline from the project needs. CI/CD means Continuous Integration and Continuous Delivery or Deployment: automatically build and check changes, then prepare or release them. The course also covers GitLab CI/CD, but the exact lecture order and instructor repo layout were not verified.

Project 3's infrastructure and playbooks are being designed from project requirements. Course provisioning scripts are not required and will not be inspected or copied; choose the target operating system (OS), the core software that runs a computer, from verified AWS, SSM, and package needs rather than script similarity.

**Runner and steps:** A runner is the temporary computer GitHub provides for a job; the hosted runner is removed when the job ends. In this workflow, checkout gets the repository and pinned submodule, setup-java installs Temurin 17 (a build of Java), and `run: bash scripts/build.sh` starts the build, so each run repeats the setup.

A **runner image** is the set of software installed on the hosted runner, such as Java and Maven. Its version appears under **Runner Image** in the Set up job log. GitHub updates images over time, so the same workflow can use different software versions on different runs; the separate **Hosted Compute Agent** block describes GitHub's runner service, not the image (verified from PR #2 logs).

**Actions, commands, and names:** A step with `uses:` runs a packaged action; this workflow uses checkout and setup-java actions from other repositories, while `run:` executes a shell command. Step names label log sections, but the workflow name feeds `github.workflow` in the concurrency group and the job name identifies the status check, so changing those names can affect cancellation grouping or required-check matching.

**SHA pinning:** SHA is short for Secure Hash Algorithm; a commit SHA is the fingerprint Git uses to identify one exact saved version. Pinning an action to its SHA selects that exact version, while a version tag is a name its owners can move. This workflow pins checkout and setup-java by SHA, so using a newer action version requires changing the pinned SHA.

**Token and permissions:** A credential is a secret, such as a password or token, used to prove identity or access. GitHub gives each workflow run a `GITHUB_TOKEN`, a temporary credential used to access GitHub, and `permissions` limits what it can do. `contents: read` allows the workflow to read repository contents without permission to push changes; `persist-credentials: false` tells checkout not to save the token as a Git credential in the repository's local configuration.

**Concurrency groups:** This workflow builds a group from `github.workflow` (the workflow's name) and `github.ref` (the branch or other Git reference for the run). With `cancel-in-progress: true`, a new run cancels an older run only when they share a group and the older run is still running; two runs on `main` share a group, while a pull request uses a different ref.

**Three triggers (verified 2026-10-07):** `push` runs after a commit lands on `main`, `workflow_dispatch` runs when you click "Run workflow" by hand, and `pull_request` runs on a proposed change before it merges. In this project, run #4 was manual (40 s), and PR #1's check passed (28 s).

**Pull request (PR):** A PR asks GitHub to merge one branch into another, such as `docs/record-phase1-checks` into `main`. GitHub tests a temporary merge of the two; the PR #2 log shows `refs/remotes/pull/2/merge`. A PR is how a change reaches `main` now.

**Ruleset and required check (verified 2026-10-07):** A ruleset is a set of rules GitHub applies to chosen branches. `protect-main` is active on `main`, requires `build-test` from GitHub Actions, and blocks force pushes. On PR #2, the failing check carried a Required badge and the Merge button was disabled. A direct push to `main` should now be refused, but that was not tested.

**Why test a failure path:** A pipeline that has only passed has not shown it can fail. In PR #2, the count pattern was changed to `99999`, so the job ended with `ERROR: Maven did not report any tests as run.` and exit code 1, even though Maven said `BUILD SUCCESS`. This shows the script's error path works. It does not show the original check rejects 0 tests, because `99999` fails for any count.

**Token permissions (verified):** The Set up job log listed only `Contents: read` and `Metadata: read`, so the workflow cannot push changes to the repository.

**Checkout credential cleanup (verified):** With `persist-credentials: false`, checkout stores a temporary credential file outside the repository and adds `includeIf` pointers to it in the repo's config. After the checkout, it removes the pointers and logs `Removing credentials config`. The hosted runner is deleted when the job ends.

**Apps that add checks (verified access, reported origin):** A GitHub App with "All repositories" access can add its own check and comment to a PR without appearing in the workflow file. SonarQubeCloud did this on PRs #1 and #2. Its Udemy-course origin is reported but not independently verified. It is not part of Project 3's scope.

## 4. Save and deliver the built app

The WAR is the packaged web app file made by the build. **Nexus** stores versioned build files; it does not build or run the app. **Amazon S3 (Simple Storage Service)** is AWS storage for files and other data. For example, a private artifact store could keep the VProfile WAR made by a successful build. **SonarQube** checks code quality. Nexus remains undecided, while SonarQube Cloud is an external PR check rather than an approved Project 3 quality gate. Neither tool is in the approved scope; adding either requires later approval.

A build number plus the source commit can identify which run made a WAR and which app version it used. A health check can see whether the deployed app responds. A rollback can return to an earlier version if the new one fails. These are planned behaviors, not completed or tested features.

The WAR must stay private. Do not put it in a public repo, release, or log. The source-use permission is unresolved, so attribution must stay and public sharing of the built WAR is not allowed unless permission is established. Under the current project instructions, a private-only copy (for example, in private S3) is an accepted risk, not permission, and still needs the design, cost, and implementation approvals.

**Private S3 and retention (D1 buckets created; role access planned):** S3 Block Public Access blocks public access; encryption protects stored data but does not decide which role can read it. D1 created both buckets with Block Public Access, S3-managed default encryption, and HTTPS-only policies; the WAR expires after 30 days and Ansible transfer files after 1 day. GitHub upload, instance download, and Ansible transfer permissions remain unimplemented.

**Why keep three separate buckets until project close (D1 buckets created; stack use planned):** The state bucket keeps Terraform's record, the WAR bucket is for build files, and the Ansible bucket is for short-lived helper files. Keeping them outside the per-session stack means destroying that stack can leave them in place, but they need separately approved cleanup and must be empty before deletion.

**Versioning, overwrite, and expiry (D1 choices; S3 behavior reported, not independently checked):** An S3 key is a file's name in the bucket. Without versioning, uploading to an existing key replaces the old file, and deleting a file removes it for good. For example, if CI uploaded a different file to `vprofile-v2-build42-9f22748.war`, the build 42 WAR would be gone. Unique keys make that unlikely but do not prevent it. A lifecycle rule that expires by age fits unique keys; "keep the last N builds" does not, because S3 counts versions of one key, not different keys. Expiry is a cleanup, not an exact timer. In a versioned bucket, expiry adds a delete marker (a record that makes the object look deleted while older versions remain), and old versions need their own rule. The Terraform state bucket is versioned with a 30-day rule for old versions; the D1 WAR and Ansible buckets are not versioned, so they have no older copies to restore.

**Health check (planned):** A health check asks whether the deployed VProfile app is ready to serve requests. The port, real app URL (web address), and response that proves the app is healthy are undecided; Tomcat, the Java web server, on port `8080` is only a candidate from memory.

HTTP (Hypertext Transfer Protocol) is a set of rules computers use to send web requests and responses. A `200` response means the request succeeded, but it may not prove the VProfile page or its dependencies are working. The check should retry while Tomcat starts and require text that only the VProfile page contains, because another program could also return `200`.

The expected text should be chosen after seeing the real response. A login-page response alone does not prove that MySQL (database software that stores app records), Memcached (a service that stores recent data in memory for quick reads), or RabbitMQ (a service that passes messages between programs) are working. The check's result must determine whether deployment succeeded.

Manual SSM port forwarding is for viewing the private app. The proposed automated check would run on the instance through SSM Run Command because a GitHub-hosted runner cannot directly reach the private instance.

**Finding the app's address (partly reported; not tested, 2026-10-11):** Tomcat normally uses a WAR's file name as the web address path: `vprofile-v2.war` would likely be at `/vprofile-v2/`, while `ROOT.war` would use `/` (general convention, not tested here). The `/` page is reported to show a login screen; a response from it alone does not prove that MySQL, Memcached, or RabbitMQ are working. The `/users` page is reported to list users' names and IDs, so it is not used as a health check.

**Rollback (planned; not built or tested):** A rollback puts the previous working WAR back if a new one fails its health check. For example, if build 42 never passes, the deployment document would download the build 41 WAR from S3, put it back in Tomcat, and run the same health check again. This needs unique S3 keys so an earlier WAR is not overwritten, a record of which build is working (where it lives is undecided), and a final result that turns the workflow red even when rollback succeeds. Rollback replaces only the WAR: it does not undo database changes, cannot work if retention has deleted every earlier WAR, and the first deployment has nothing to return to. Demonstrating it needs a deliberately failing deployment, which needs separate approval.

**Security rules and the filter (code reading; not tested, 2026-10-11):** A filter is code that checks every web request before the app answers it. `appconfig-security.xml` says `/` needs a logged-in user, but that rule works only if a filter loads it. A search under `src/main` found no filter registration, so the rules may not apply; only a running app shows which is true.

## 5. Add AWS resources only after the design and cost gate

**Terraform** is planned to create cloud resources such as networks, computers, and permissions from configuration files. **Ansible** is planned to install software and set up computers and apps. See **Terraform state, backend, and locking** below for the proposed remote S3 state, encryption, versioning, and lock settings.

An AWS **IAM (Identity and Access Management) role** is an AWS identity that gives a computer limited permissions. For example, a build computer should get only the AWS access it needs. Jenkins credentials are stored passwords or tokens used by tools. Do not commit passwords or keys. AWS Secrets Manager is a managed AWS service for storing and retrieving sensitive values such as passwords and keys.

**SSM access (planned):** SSM means AWS Systems Manager. Session Manager lets a person open a shell or forward a port to an EC2 instance. The SSM Agent starts outbound connections (from the instance to AWS), so Session Manager does not need inbound connections (new connections coming from outside toward the instance) or SSH (Secure Shell, a way to open a remote command session). It does not give the instance general internet access. The planned choice favors managed access without opening SSH; the trade-off is that the agent, IAM permissions, and a working network path must all be present.

**Port forwarding (planned):** A port is a number that directs a connection to a program, such as Tomcat. The SSM Agent is a background program on the instance that connects it to Systems Manager. SSM port forwarding connects a local port to the instance through the Agent's outbound session, so it needs no inbound connection. In `http://localhost:8080`, `localhost` means this computer, and the request is forwarded to the chosen Tomcat port on the instance. The forwarded connection works only while the local command is running. `8080` is an example only; the target port still needs confirmation.

**Private network and updates (planned design):** A network connects computers so they can send data. A subnet is a smaller part of a network, and a VPC (Virtual Private Cloud) is a private network in AWS. A route tells network traffic where to go. A public subnet has a route to an internet gateway (an AWS connection from a VPC to the internet); a private subnet does not route directly to that gateway.

NAT (Network Address Translation) lets a private computer start internet connections without its own public address. The planned private subnet plus NAT lets the instance reach SSM and software-download sites without a public IP. Compared with the cheaper public-subnet fallback, NAT adds hourly and data-processing costs; compared with SSM interface endpoints, it can reach more software sites.

If NAT is the only outbound path, deleting it while keeping the instance stops SSM and package access. The per-session destroy-and-rebuild plan avoids leaving an unreachable instance; regional NAT prices and data use must be checked before implementation.

**NAT Gateway cost model (planning estimate):** A NAT Gateway has an hourly charge and a per-GB data-processing charge; internet data transfer may add another cost. The project estimate uses reported example rates of $0.045 per gateway-hour and $0.045 per GB, not a verified current N. Virginia quote. Check the AWS Pricing Calculator for the selected Region before billable implementation. [VPC pricing](https://aws.amazon.com/vpc/pricing/), [EC2 cost formula](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-instance-addressing.html), [2023 us-east-1 example](https://aws.amazon.com/blogs/networking-and-content-delivery/identify-and-optimize-public-ipv4-address-usage-on-aws/).

**Public-IP fallback (planned):** A public IPv4 address and route to an internet gateway let an instance start outbound connections. A security group is an AWS network filter for an instance; with no inbound rules it blocks new incoming connections to the instance, but the public address makes accidental inbound-rule changes a larger risk and departs from the private-subnet design.

**Package setup:** SSM interface endpoints provide a private path from the VPC to SSM, but not to arbitrary package sites. An S3 gateway endpoint routes a VPC's traffic to S3 without NAT and has no hourly endpoint charge; it does not reach package sites. A prepared Amazon Machine Image (AMI), a saved disk image for starting an EC2 computer, can include software before an instance starts, but it must be rebuilt to receive later package and security updates.

**OIDC and access keys (planned choice):** An AWS access key is an ID and secret that a program uses to sign in; it stays usable until disabled or deleted. OIDC (OpenID Connect) lets a GitHub Actions run prove its identity with a short-lived token. The proposed trust rule accepts only this repository's `main` branch: trust decides who may use the role, while its permissions policy and boundary decide what it may do. OIDC avoids storing a long-lived AWS key in GitHub, but the trust rule must be exact and the temporary credentials remain sensitive until expiry; pull-request runs must get no AWS credentials. The [AWS guide](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp-oidc.html) describes repository and branch restrictions; exact claim conditions and workflow-level restrictions remain unverified.

**Temporary credentials and logs (planned):** Temporary AWS credentials stop working at expiry, which limits how long a leaked value can be used. They are still sensitive while valid, so never print them in a public workflow log.

**Long-lived and temporary credentials:** Temporary AWS credentials include a session token and expire; long-lived access keys do not expire automatically. Deactivating a key can be undone, but deleting it cannot, so check its last-used details and dependencies before retiring it.

**Trust and permissions policies (planned):** An IAM role has a trust policy that says who may use it and a permissions policy that says what it may do. The proposed GitHub role would trust only this repository's `main` branch and upload the WAR or start the limited deployment command; the instance role would read the WAR and support SSM. These separate roles have not been created.

**Permission sets and service roles:** An IAM Identity Center permission set defines what a person may do after signing in. A service role gives AWS access to a program, such as GitHub Actions or an EC2 instance; these are separate identities.

**Instance profile (planned):** An instance profile attaches an IAM role to an EC2 instance. The instance can then receive temporary AWS credentials for actions such as downloading the WAR, instead of storing a long-lived key on disk.

**SSM command document (planned):** An SSM document defines a command that Systems Manager can run on an instance. The proposal limits the GitHub role to one custom document on one named instance and excludes a general shell document. This narrows what the role can run, but cannot prevent a mistake inside an allowed deployment, such as choosing the wrong WAR; the document, exact permissions, health check, and rollback are still untested.

**Secrets in a public repository:** GitHub secrets are not shown just because a repository is public. Workflow code or an action that can read a secret could still expose it, so a long-lived AWS access key should not be treated as safe just because it is stored as a secret.

**Planned GitHub-to-instance path:** The proposed `main` workflow would upload the WAR to private S3, then use Systems Manager Run Command (AWS's way to send a command to an instance managed by SSM). The private instance would download the WAR using its own limited IAM role; the hosted runner would not open an inbound connection to it. Pull-request runs must have no AWS access. The exact AWS rules, permissions, and network route remain unapproved and unimplemented.

**Terraform state, backend, and locking (S3 migration completed; verification recorded 2026-10-17):** State is Terraform's record of the resources it manages; a backend is where Terraform stores that record. The bootstrap first used local state because it created the bucket that would later hold the state. I chose to migrate it to the existing S3 bucket before Phase D to test the backend, lock, and object permissions early. Keeping state local is simpler but ties it to one computer; S3 adds access-control work and makes the bucket hold the record of its own creation. The `s3:DeleteBucket` deny protects only the `p3-terraform` role. State can contain sensitive values, so keep it out of Git and restrict access. S3 versioning preserves earlier object versions, but this bucket's lifecycle rule expires noncurrent versions after 30 days. `use_lockfile = true` asks Terraform to lock state during operations that could write it. The migration completed and a later plan reported no changes; the state lineage change remains unexplained (see below). [HashiCorp S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3), [Terraform state](https://developer.hashicorp.com/terraform/language/state), [Terraform state lineage and serial safeguards](https://developer.hashicorp.com/terraform/language/state/backends).

**State-bucket bootstrap:** Terraform needs an S3 state bucket before the main configuration can use it as a remote backend. A separate bootstrap configuration first used local state to create that bucket, avoiding the loop of needing a bucket before Terraform can create one. Terminal checks reported on 2026-10-17 showed versioning, SSE-S3 (server-side encryption with keys managed by S3), Block Public Access, a 30-day rule for older object versions, and the HTTPS-only policy applied. The lifecycle rule targets noncurrent (older) versions; it does not expire the current object. The bootstrap state was later migrated to `bootstrap/terraform.tfstate` in this bucket and checked with a no-change plan. Encryption changes stored data into a form that needs the right key to read; state and lock-file objects also need separate IAM permissions from bucket settings.

**Separate Terraform configurations (planned; stack not created):** Keep `infra/bootstrap/` for the state bucket and its state; put short-lived network and application resources in `infra/stack/` with a separate key, proposed as `stack/terraform.tfstate`. The plan is to destroy only the stack configuration after a lab session, leaving the bucket and bootstrap record in place; one configuration for everything could put the state bucket on the same destroy list as the resources it records. This separation makes cleanup safer but needs another state key and new `p3-terraform` object permissions; neither is approved or implemented.

**Terraform validation:** `terraform validate` checks that the local configuration is written in a form Terraform and the selected provider (a Terraform add-on that knows how to manage a service such as AWS) accept. It does not contact AWS, prove that permissions work, or check whether the bucket name is available.

**Terraform and Ansible (planned design):** Terraform creates the network, permissions, and EC2 instance; Ansible configures software on a computer that already exists. Keeping those jobs separate makes infrastructure lifecycle changes distinct from repeatable operating-system setup. The trade-off is another tool and handoff to manage, including controller permissions and the SSM connection; using only a startup script could be simpler for one host but would make configuration reuse and reruns harder to manage.

**Ansible playbook and idempotence (planned):** A playbook lists setup tasks, such as installing MySQL, writing its configuration, and starting its service. Idempotence means a second run leaves an already-correct computer unchanged, because the packages, settings, and services already match the request. This makes reruns safer, but tasks must check the current state; a command that blindly repeats an action may not be idempotent.

**Ansible over SSM (plugin details reported; not independently verified):** The `amazon.aws.aws_ssm` connection lets Ansible manage an instance through Systems Manager sessions instead of SSH; the proposed GitHub deployment uses Run Command (`SendCommand`), which is a different path. In the reported flow, the Ubuntu WSL controller uploads helper files to a separate Ansible transfer bucket and supplies a presigned URL for the instance to download them (see below). This bucket has a temporary-file purpose separate from the WAR and Terraform state buckets.

**IAM Identity Center and CLI sessions (reported; AWS pages not independently reviewed):** IAM stores users, roles, and policies, while Identity Center handles human sign-in and permission sets. SSO means single sign-on, or one sign-in used to access services. In the proposal, `aws sso login` would provide temporary role credentials; the cited AWS pages report a one-hour default for role credentials and an eight-hour default for the sign-in session, with role credentials refreshed while that session remains valid. **Role permission boundaries (planning choice; action lists unverified):** For identity-based permissions in this design, an action requires both the role policy and its permissions boundary to allow it; a boundary does not grant permission by itself. The plan uses `p3-instance-boundary` for the EC2 role and `p3-github-boundary` for the GitHub role. Separate boundaries fit their different jobs: a shared boundary would need the union of both jobs' allowed actions, while two boundaries can give each role a narrower ceiling. This is easier to review by role but means two policies must be kept correct; a narrowly scoped IAM-setup permission set would create them, and Terraform could not edit them. A separate boundary on the controller permission set remains undecided.

**Permissions-boundary example (worked through 2026-10-17):** In a simple identity-policy example, the role policy allows `s3:GetObject` and `s3:PutObject`, while the boundary allows only `s3:GetObject`. The role can read the object, but it cannot save one: `s3:PutObject` is missing from the boundary. A boundary sets the ceiling; it does not grant an action by itself. This is an implicit denial: AWS refuses the action because no policy allows it, even though no explicit `Deny` rule is written. Explicit denies and other policy types can also affect the final result. [AWS permissions boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html).

**Tags for generated resources:** A resource tag is a small name-and-value label attached to an AWS item. VPCs, subnets, and EC2 instances have generated IDs, so a `p3-` name prefix cannot identify them. A tag such as `Project=p3` can help scope access, but the policy must also control who can add, change, or remove that tag; the exact IAM conditions depend on the action.

**Permission-list outline (planned; drafts later checked against source reviews, none tested):** The design separates access into three permission sets and two service roles, each with its own allowed actions and resources. The GitHub role uploads the WAR to one bucket and starts one SSM document on one instance, without delete permission or a general shell document. The instance role lets the SSM Agent (software that connects the instance to Systems Manager) manage the instance and lets the instance read the WAR; it needs no IAM-management or S3 write permissions. The Ansible/SSM set opens sessions and uses the transfer bucket. The `p3-terraform` set gains object permissions for a `stack/terraform.tfstate` key and its `.tflock` object. A rare IAM setup set creates the two boundary policies, so Terraform cannot widen the ceiling that limits the other roles; the trade-off is one more set to create, assign, and later remove. The drafts were checked against source reviews (see the Phase D section below) but none has been tested; a missing permission can produce `AccessDenied`, AWS's message that the request is not allowed.

**IAM user and least privilege (reported, 2026-10-11):** An IAM user is a named identity in an AWS account; least privilege means giving it only the actions its job needs. ### Identity setup and least-privilege checks (updated 2026-10-16)

**Organization and Identity Center instance:** An AWS Organization groups accounts under a management account (the account that manages the group). An IAM Identity Center organization instance is attached to that Organization and can provide permission sets across its accounts; an account instance is scoped to one account and does not create an Organization. An AWS Region is a geographic area where AWS runs resources; Availability Zones are separate locations within a Region. This project used the organization instance in `us-east-1` with a single-Region setup; the primary Region is reported as fixed after enablement. These details were reported from research notes and console screenshots; live AWS settings were not rechecked.

**Human user, permission set, and assignment:** An Identity Center user is a person’s sign-in identity. A permission set is a named collection of AWS permissions, and an assignment connects that set to a user for an AWS account. This is different from an IAM user with an access key, and both are different from a service role used by GitHub Actions or an EC2 instance.

**CLI profile and temporary role credentials:** `aws configure sso` created the named `p3-readonly` profile and `p3` SSO session in Ubuntu WSL (Windows Subsystem for Linux, which runs a Linux environment on Windows). The profile records sign-in and role settings; it is not a permanent access key. The `get-caller-identity` result contained `assumed-role`, which showed that the CLI used temporary role credentials; credential expiry was not observed. In this setup WSL could not open a browser, so sign-in approval happened in a Windows browser and returned to the waiting CLI through a local callback address (a local web address the CLI waits on for the sign-in result).

**Permission-set creation and reprovisioning (reported from console screenshots and terminal output, 2026-10-16):** `p3-terraform` was created as a custom permission set with an inline policy (policy text attached directly to the set), no managed policies (reusable policies provided separately), no permissions boundary or tags, and a one-hour session. The account-assignment success banner was not captured, but the role appeared in the CLI role list and `aws sts get-caller-identity` later showed its assumed-role identity. This command asks AWS to identify the credentials in use. After the approved `s3:PutBucketAcl` policy edit, the console reported that the assignment was reprovisioned, meaning the updated permission set was applied to its account role. This confirms that the policy update was pushed, not that the extra action was needed.

**Terraform plan and saved-plan handling (reported from terminal output, 2026-10-16):** At that time, the plan showed five resources to add and no changes or deletions. Because the bucket did not exist then, the plan tested read access but did not test write permissions. `terraform plan -out=tfplan` saved a plan file; `terraform apply tfplan` applies that saved plan without an interactive confirmation. Review the saved plan and get explicit approval before applying. Keep plan files out of Git, and create a fresh plan after changing the Terraform configuration or permission policy.

**A 404 does not reserve an S3 name:** HTTP 404 means “not found.” The `head-bucket` command asks whether a bucket responds; it returned 404 for the planned state bucket and later for the WAR and Ansible names before creation. General-purpose S3 names share a global namespace, so another account could claim a name before the create request; the check does not reserve it. [AWS naming rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html).

**Why `s3:PutBucketAcl` was removed (reported from policy text, console screenshot, and terminal output, 2026-10-17):** An ACL (access control list) is a permissions list for a bucket or object. This configuration does not set an ACL; provider `v6.69.1` defaults to private, and AWS says an omitted or private ACL on `CreateBucket` needs only `s3:CreateBucket`. The extra `s3:PutBucketAcl` action was removed from the create/configure statement and the permission set was reprovisioned. After a fresh sign-in, a plan refreshed six existing resources and reported no changes, showing that reads still worked; it did not test creating a new bucket without the action, because the original bucket was created while the action was allowed. No bucket was destroyed just to run that test. This narrows the permissions based on provider and AWS documentation while leaving new-bucket creation untested; `s3:GetBucketAcl` is a separate read action and remained in the policy. [Provider source](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/s3/bucket.go#L3658-L3667), [AWS CreateBucket permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateBucket.html).

**HTTPS-only policy (applied and verified 2026-10-17; AWS guidance reported, not independently opened):** HTTPS is a web connection protected with encryption while it travels; HTTP does not provide that transport protection. SSE-S3 means server-side encryption with S3-managed keys and protects stored objects. A bucket policy is a rule attached to a bucket that controls requests, and its `Deny` for `aws:SecureTransport=false` makes S3 reject HTTP requests. The policy was applied to the state bucket, and a live `get-bucket-policy` read-back showed the `DenyInsecureTransport` rule; `terraform plan` then reported no changes. Denial of a real plain-HTTP request was not tested. Terraform and the AWS CLI already use HTTPS, so the policy mainly guards against a misconfigured client. It does not protect local copies of the state file.

This policy names both the bucket ARN (Amazon Resource Name, AWS's full resource name) and its `/*` object ARN, so it covers matching bucket-level and object requests. A client-side HTTPS convention only governs that client; the bucket policy applies to requests from any caller that match the deny condition. AWS warns that some service-to-service calls may not include transport details in the policy context. A future AWS service integration may therefore need an exception such as `aws:PrincipalIsAWSService=false` in the deny condition.

**Interview explanation:** “The bucket policy denies HTTP requests to the bucket and its objects when they match the deny condition. HTTPS protects data while it travels; SSE-S3 protects stored objects. We verified the stored policy with `get-bucket-policy`, but did not test a plain-HTTP request. The trade-off is another managed policy and its IAM lifecycle permissions, with possible exceptions for future AWS service integrations.” [AWS transport-security guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryptionInTransit.html), [AWS condition-key guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html).

**S3 server access logging (risk accepted, 2026-10-17):** Server access logging creates records for later review of S3 requests. A record can show the requester when available, bucket or object key, time, operation, HTTP status, and S3 error code. AWS delivers logs on a best-effort basis, so entries can be late or missing; an error code may not explain the full cause. The S3 destination considered here would be a separate bucket in the same account and Region; S3 does not charge for log delivery, but stored log objects incur storage charges. AWS documents CloudWatch Logs (AWS's service for storing and viewing logs) as another supported destination, but this option was not evaluated. The fourth-bucket rationale below applies only to the S3 destination considered. AWS CloudTrail (which records AWS activity) data events (records of actions on S3 objects, such as reads or writes) were discussed, but their scope and cost were not checked. Logging stayed disabled as an accepted risk: the stated rationale was that one role used the bucket, it was private, encrypted, versioned, and HTTPS-only, and an S3 log bucket would add a fourth bucket beyond the approved three-bucket design. This accepts less audit history; revisit if other identities use the bucket. The PR #26 SonarCloud issue and its status were not checked during this 2026-10-17 review. PR #44 later reported two separate open logging findings on the D1 WAR and Ansible buckets; see the D1 entry below. [AWS server access logging](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ServerLogs.html), [log record fields](https://docs.aws.amazon.com/AmazonS3/latest/userguide/LogFormat.html), [S3 logging options](https://docs.aws.amazon.com/AmazonS3/latest/userguide/logging-with-S3.html).

**Terraform S3 bucket-policy API calls and IAM scope (reported from provider `v6.69.1` source and the AWS S3 action reference, 2026-10-17; links not independently opened):** An API (application programming interface) is a set of rules that lets one program send a request to another service. The reported provider calls for create and update are `PutBucketPolicy`; it reads the policy with `GetBucketPolicy`, and create/destroy waiters (repeated status checks) also poll with `GetBucketPolicy`. Destroy calls `DeleteBucketPolicy`. The first apply returned `AccessDenied` for `s3:PutBucketPolicy`; the later `get-bucket-policy` read-back (a command that asks AWS to return the current policy) showed that `s3:GetBucketPolicy` worked.

Full lifecycle management therefore needs `s3:PutBucketPolicy`, `s3:GetBucketPolicy`, and `s3:DeleteBucketPolicy`, each scoped to the state bucket ARN `arn:aws:s3:::p3-vprofile-tfstate-x4b8t3`, not an object ARN. `s3:DeleteBucketPolicy` removes the policy and is distinct from `s3:DeleteBucket`, so it does not grant permission to delete the state bucket. **Bucket ARN versus object ARN:** An ARN is AWS's full resource name. The bucket ARN, such as `arn:aws:s3:::p3-vprofile-tfstate-x4b8t3`, names the bucket itself; adding `/` and an object key names one object inside it, for example `arn:aws:s3:::p3-vprofile-tfstate-x4b8t3/bootstrap/terraform.tfstate`. A policy must match both the action and the resource: `s3:ListBucket` applies to the bucket ARN, while `s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject` apply to object ARNs. A bucket-level permission therefore does not grant permission to read or save a state file. `infra/bootstrap/backend.tf` names `bootstrap/terraform.tfstate`, and the migration placed the state object at that key. [HashiCorp S3 backend permissions](https://developer.hashicorp.com/terraform/language/backend/s3), [AWS S3 actions and resources](https://docs.aws.amazon.com/service-authorization/latest/reference/list_s3.html).

**S3 backend object permissions (HashiCorp's documented minimum):** The backend `key` is the object's name/path inside the bucket, and `use_lockfile = true` puts the lock object at that key plus `.tflock`. For that workspace, HashiCorp documents `s3:ListBucket` on the bucket ARN, `s3:GetObject` and `s3:PutObject` on the state object ARN, and those same two actions plus `s3:DeleteObject` on the lock object ARN; normal state saves do not need permission to delete the state object. [HashiCorp S3 backend permissions and key format](https://developer.hashicorp.com/terraform/language/backend/s3).

**SSM command and session scope (author-checked source review, 2026-10-19; no policy test):** `ssm:StartSession` is scoped to the target instance and Session Manager document; `ResumeSession` and `TerminateSession` use the session ARN pattern `session/${aws:userid}-*`, which matches sessions for the caller's AWS identity. `ssm:SendCommand` names both the custom document and target instance, while the draft uses `Resource: "*"` for `ssm:GetCommandInvocation` because no resource-level scope was found. `ssmmessages:OpenDataChannel` stays on `"*"` because the formal action reference lists no resource type, while some AWS examples show a session ARN; a live session has not tested whether that ARN works. **IAM actions and resources (learning example, 2026-10-15):** `Action` names what Terraform may do; `Resource` names what it may do it to. With `s3:PutBucketVersioning`, one bucket ARN permits versioning changes on that bucket, while `Resource: "*"` keeps the action the same but lets it apply to every bucket the action supports. `Action: "*"` is a separate widening of operations, so a star in one field does not automatically make the other field a star.

**Build Terraform permissions from jobs (planned):** Start with a job such as creating the state bucket, then list only the AWS operations and resources that job needs. This makes each permission easier to explain and can limit the damage from mistakes. A broad administrator policy would be quicker to begin with, but would grant unrelated actions and hide missing permissions; the job-based method takes more review because Terraform also needs provider reads and dependencies.

**Reading the Job 1 state-bucket policy (2026-10-16):** `Sid` is an optional label for people reading the policy; it does not change access. `Version` selects the policy language, not an expiry date; `Effect` says allow or deny, `Action` names an AWS operation, and `Resource` names the target bucket by its full AWS resource name (ARN).

**Why the policy names exact actions and one bucket:** The design lists the S3 operations Terraform needs instead of granting `AdministratorAccess` or every S3 action (`s3:*`), and names only `p3-vprofile-tfstate-x4b8t3`. **Why bucket deletion is denied:** An explicit `Deny` for `s3:DeleteBucket` wins over an `Allow` for that action, so Terraform cannot remove the state bucket during ordinary stack cleanup. This keeps the bucket that stores Terraform's record beyond a session's destroy, but project-close deletion needs a separate approved step. The deny protects the bucket from deletion only; it does not protect its settings or the objects inside it.

**Bucket permissions and state-file permissions:** Bucket setup actions and `s3:ListBucket` apply to the bucket itself. State and lock-file actions apply to object ARNs, so the backend needs separate object permissions even when the same role already manages the bucket. ### Phase D permission and infrastructure design

**Source checks and limits:** The permission drafts were checked against AWS documentation and versioned provider/plugin source. Selected official pages were reportedly opened during this documentation pass. Not every action mapping was rechecked, and the effective AWS permissions were not tested; a first plan or run can still fail if an action is missing or the active role differs from the draft.

**GitHub OIDC trust:** OpenID Connect (OIDC) lets a workflow prove its identity to AWS with a short-lived signed token instead of a long-lived AWS key stored in GitHub. The role trust policy decides who may assume the role; its permissions policy decides what the role may do. `aud` (audience) says the token is meant for AWS STS, and `sub` (subject) identifies the repository and branch.

**Exact OIDC subject:** For `main`, the trust draft uses exact `StringEquals` conditions on `aud=sts.amazonaws.com` and `sub`; an exact match means the text must match exactly. GitHub uses a different `sub` when a workflow uses an environment or a pull request. Repositories created after 2026-07-15, and those opting into immutable subject claims, use owner and repository IDs in `sub`, so read the actual claim before writing the trust policy. [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).

**GitHub deployment permissions:** The roughly 83 MB WAR is larger than the AWS CLI's default 8 MB multipart threshold, so `aws s3 cp` uploads it in parts. The draft allows `s3:PutObject` and `s3:AbortMultipartUpload` on WAR object ARNs, and `ssm:SendCommand` on the custom document and instance; `ssm:GetCommandInvocation` uses `*`. A unique key containing the build number and source commit helps retain older builds for rollback instead of replacing one key. [AWS CLI multipart setting](https://docs.aws.amazon.com/cli/latest/topic/s3-config.html).

**Preventing an accidental overwrite:** S3 supports an `If-None-Match: *` conditional write, which fails if the key already exists; a bucket policy can require the `s3:if-none-match` condition. Whether the planned `aws s3 cp` command sends that header is unconfirmed, so overwrite protection remains undecided and unique keys remain the current design.

**Conditional writes with multipart uploads:** The upload-start and part-upload requests do not carry the conditional header. AWS's example uses `s3:ObjectCreationOperation` to handle those steps while requiring the condition on the completed upload. [Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [enforcing conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).

**Ansible controller bucket access:** The controller uploads a helper file to the transfer bucket and gives the instance a presigned URL, so the instance needs no lasting access to that bucket (see the presigned URL entry above). The plugin's `HeadBucket` check needs `s3:ListBucket`. Dropping `GetBucketLocation` remains a recommendation, not a decision.

**Instance role and SSM agent:** The draft gives the instance role `ssm:UpdateInstanceInformation` and four message-channel actions—`ssmmessages:CreateControlChannel`, `CreateDataChannel`, `OpenControlChannel`, and `OpenDataChannel`—on `*`. SSM Agent 3.3.40 or later uses `ssmmessages` whenever available; `ec2messages` is supported only in Regions launched before 2024. Because the AMI's agent version is unknown and AWS publishes no minimum permission list for Run Command alone, this small set is an inference to test. [AWS message API guidance](https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-setting-up-messageAPIs.html).

**Instance role and WAR download:** The instance role needs `s3:GetObject` on the WAR object ARNs, but the draft leaves out `s3:ListBucket`; if the key is wrong, S3 can return 403 (denied) instead of 404 (not found) because the role cannot list the bucket. SSE-S3 (`AES256`) uses S3-managed encryption, so the draft needs no KMS key permissions for this bucket. The reviewed action list found no additional IAM action for downloading a large object; the same `s3:GetObject` permission applies.

**Permissions boundaries:** A permissions boundary sets the maximum actions an identity policy may grant; it does not grant actions by itself. An action succeeds only if both the role policy and the boundary allow it. The draft uses `StringEquals` with `iam:PermissionsBoundary` to require the approved boundary ARN when Terraform creates a role or attaches permissions to it.

**Protecting the boundary:** The draft explicitly denies `iam:CreatePolicyVersion`, `iam:DeletePolicy`, `iam:DeletePolicyVersion`, and `iam:SetDefaultPolicyVersion` on the two boundary policy ARNs. It also denies `iam:DeleteRolePermissionsBoundary` on protected roles and prevents `iam:PutRolePermissionsBoundary` from replacing the boundary with another ARN.

**Boundary limit:** A same-account resource policy that names a role session directly can grant permissions outside an implicit boundary deny. The boundary therefore limits the role's identity policies, but is not a complete account-wide guardrail. [AWS permissions-boundary guide](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html).

**Why use a rare IAM setup identity:** A rarely used identity creates the two boundaries and GitHub's OIDC provider, while the routine Terraform identity cannot change or detach them. This makes the guardrails harder for routine infrastructure changes to remove; the cost is a separate sign-in and Terraform state to maintain.

**Why keep the buckets in `infra/bootstrap/`:** Bootstrap holds the state, WAR, and Ansible buckets so destroying the application stack does not delete them. D1 created five Terraform resources (managed AWS items) for each new bucket: the bucket, encryption, public-access block, lifecycle rule, and HTTPS-only policy. See the bucket retention trade-off below.

**Why D1 used separate bucket permission statements:** An IAM statement is one allow-or-deny rule. D1 gives the WAR and Ansible buckets separate create/configure, read, and bucket-policy statements instead of extending the state-bucket statements; this adds policy text but keeps versioning permission out and matches each bucket's job. The shared `s3:DeleteBucket` deny lists all three bucket ARNs, but protects only this permission set; cleanup still needs separate approval.

**Why permission-set reprovisioning matters:** A permission set is the template IAM Identity Center uses to create or update an account role. Reprovisioning sends saved changes to that role, and a new sign-in starts a session with the updated permissions. The console reportedly showed D1 reprovisioning succeeded, but the saved JSON was not read back there.

**Why put the new buckets in `buckets.tf`:** Terraform loads all `.tf` files in one folder as one configuration. The new file keeps the state bucket's `main.tf` text untouched, while Terraform still plans the new buckets together with the existing bootstrap resources. A separate file is for organization; it does not create a separate Terraform state or isolate the buckets from the bootstrap configuration.

**Why save and apply `d1.tfplan`:** The plan and saved file showed 10 additions, 0 changes, and 0 deletions. Applying a saved plan uses those reviewed changes; a plan is only a preview and does not test AWS write permissions. The supplied apply output ends with ten resources added, but earlier lines were not supplied; `d1.tfplan` is ignored by Git, and the older `tfplan` is stale.

**What D1's read-back proved:** The state listed 16 resources after the apply. Live reads showed S3-managed `AES256` encryption and all four Block Public Access settings set to `true` on each bucket, the expected lifecycle rules, and each HTTPS-only policy. Reading a policy proves its saved text, not that a plain-HTTP request was refused; bucket and policy deletion were not tested, and tag removal and the saved permission-set JSON were not checked.

**What Terraform formatting and validation checks prove:** `terraform fmt -check` reports formatting differences without changing files. `terraform validate` checks that the configuration and its references fit together; neither command contacts AWS or proves the caller has permission to create resources.

**Why the apply command names a folder and plan:** From the repository root, `cd infra/bootstrap` selects the Terraform folder; `&&` runs apply only if that succeeds. `terraform apply d1.tfplan` uses the saved plan and skips Terraform's interactive confirmation, so separate approval is still needed before running it. The final `; cd ../..` runs even if apply fails and can hide Terraform's exit code; inspect the apply output.

**Bucket retention trade-off:** The two D1 buckets have no versioning, so older copies cannot be restored after an object is overwritten or deleted. Planned unique WAR keys keep builds separate until the 30-day lifecycle rule expires them; temporary Ansible files expire after 1 day. `force_destroy = false` makes Terraform stop if a bucket still contains objects, so cleanup must empty it first.

**D1 bucket logging findings (reported from PR #44, 2026-10-19):** SonarQube Cloud reported two Medium `terraform:S6258` findings because server access logging was disabled on the WAR and Ansible buckets. Both were Open; neither was marked Accepted or resolved. In SonarQube Cloud, accepting an issue defers its fix and removes it from quality reports and ratings, so keeping these findings open preserves their visibility until the logging choice is made. S3 server access logs can be delivered to an S3 general purpose bucket or CloudWatch Logs, but delivery is best effort and records can be late, duplicated, or missing. At the D3 design gate, before the GitHub and instance roles first use these buckets, compare leaving logging disabled and documenting the risk with enabling either supported destination, including its costs. The PR screenshot showed a C Security Rating on new code, but did not confirm that these two findings caused it. [AWS server access logging](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ServerLogs.html), [SonarQube Cloud issue statuses](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/issues/editing).

**Why put long-lived IAM objects in `infra/iam/`:** This configuration creates the two boundaries and one OIDC provider under state key `iam/terraform.tfstate`. Manual CLI creation would be quicker, but harder to repeat and review.

**Why use a separate `infra/stack/`:** It holds the network, roles, SSM document, and one application instance under `stack/terraform.tfstate`. Its state can be destroyed and rebuilt without deleting the buckets, boundaries, or OIDC provider; the trade-off is one more Terraform configuration and state key to maintain.

**One-instance layout:** Keeping services on one host and reaching it through SSM, with no public IP or inbound rule, is simpler for this lab. It is one point of failure and depends on correct loopback binds; the preliminary comparison showed nearly equal compute cost for one `t3.large` and four `t3.small` instances.

**Instance metadata:** IMDS (Instance Metadata Service) gives software on an EC2 instance its temporary role credentials. IMDSv2 requires a token before software can read them, and hop limit 1 limits the response to one network hop. Container compatibility was not tested.

**Provider checks: security group and NAT:** The `hashicorp/aws` 6.69.1 source review found that the provider removes the security group's default egress rule at creation, so outbound rules can be set explicitly. Deleting a NAT Gateway and releasing its Elastic IP are separate actions, so both permissions are needed.

**Provider checks: launching the instance:** One `RunInstances` request can refer to multiple resource types, such as the AMI, subnet, security group, instance, and volume; IAM must authorize each supported type, but this does not mean Terraform launches several instances. `iam:PassRole`—permission to hand a role to an AWS service—is limited to the instance role with `iam:PassedToService=ec2.amazonaws.com`.

**Provider checks: other open items:** The AMI lookup uses an AWS-published SSM parameter ARN with no account ID. `DescribeIamInstanceProfileAssociations` remains a proposed read action, not an accepted one, and the S3 tag-on-create condition is unconfirmed. These findings explain why a hand-written permission list is longer than the visible Terraform resource count, but do not prove the exact calls in a run. [AWS provider source, v6.69.1](https://github.com/hashicorp/terraform-provider-aws/tree/v6.69.1).

**EBS root-volume encryption (open):** EBS (Elastic Block Store) provides the virtual disks EC2 instances use. The root volume is the disk that holds the instance's operating system and files. SSE-S3 protects S3 objects; it does not encrypt that EBS disk. The plan assumes an unencrypted root volume, but the account's default EBS encryption setting was not checked and can override that assumption. Confirm the setting and selected KMS key, then review the launch identity's key-use permissions before applying. [AWS EBS encryption](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-encryption.html), [permissions for encrypted EBS](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-encryption-requirements.html).

## 6. Check AWS costs and live resources carefully

Stopping an EC2 computer stops its compute use, but storage and other resources can still cost money. A VPC is an AWS private network; the VPC itself has no hourly charge, while some resources in it can. An Application Load Balancer has its own billing line. Interface VPC endpoints can charge by the hour even when idle; S3 gateway endpoints have no endpoint-hour charge. Check current prices before making a cost decision.

Bills can update late. Cleaning up stops later use but does not remove earlier charges. A bill can show a charge and a separate credit that subtracts from it, so a zero total does not mean there was no usage. Cost Explorer can group charges by usage type. A service line alone may not prove which resource caused it.

**Hourly costs and teardown (planned):** Stopping an instance stops its compute charge, but its EBS (Elastic Block Store) disk, the virtual computer's persistent storage, can keep billing until deleted; NAT Gateways, public IPv4 (internet protocol version 4) addresses, and SSM interface endpoints can also keep hourly charges while they exist. Way 1 proposes destroying the stack after each session and rebuilding it, which gives a fresh database next time. The separate state and WAR buckets may remain and incur storage charges, so check Terraform state and live AWS resources after destroy.

Earlier checks found that an empty `aws s3api get-bucket-versioning` response meant versioning was not enabled for that bucket. `aws secretsmanager list-secrets --include-planned-deletion` also shows secrets waiting to be deleted; active secrets are billed monthly. Ansible's SSM connection can put temporary files such as `AnsiballZ_ping.py` in S3 while it works. These facts do not identify which project owns a bucket or secret.

An S3 gateway endpoint for Project 1 was reported as still present and free; a later check found one, but did not prove its owner. Project 2 interface endpoints were reported as removed, but raw command output is unavailable, so that report was not independently checked.

AWS CLI `describe-*` and `list-*` commands inspect settings without changing them. Most regional EC2 and VPC checks used `--region us-east-1`. Route 53 (AWS's DNS service) hosted-zone listing is global and has no region option. AWS CLI `--query` uses JMESPath, a small language for picking fields from command results; `...[].[A,B]` selects two columns. Cost Explorer can group charges by usage type and show regions with usage. `AWS_PAGER=""` prevents output from pausing, and `--output table` makes a table.

## 7. Read command results before trusting them

`terraform state list` shows resources recorded in the selected Terraform state. `terraform plan -destroy` refreshes the state and previews what Terraform would remove; it does not remove anything. Compare that list with live AWS resources because something created outside Terraform may be missing from the state.

Git Bash maps the Windows `G:` drive to `/g`; quote a path that contains spaces, for example `"/g/Tutorial Folder/..."`. `pwd` shows the current folder, and `git rev-parse --show-toplevel` prints the Git repository root; use it to confirm you are in `cicd-pipeline-vprofile`, not the nested `vprofile-src/` repo. A plain folder copy without `.git` is not a Git repo, so Git commands fail there. Clear the command line before pasting; leftover text can join the next command and break it.

A syntax check, a Maven log, a created WAR, and the script's final success message prove different things. For example, `bash -n` checks only syntax, while the Maven log and WAR show that a build ran; keep the evidence and current project status in `PROGRESS.md`.

**`git pull --ff-only origin main`:** `origin` is the remote's short name, and `main` is the branch to update. `--ff-only` moves local `main` forward when it is simply behind the remote; if the histories have diverged, Git stops instead of making a merge commit. This is useful after creating a file through GitHub's web UI (user interface, the web page and controls you use).

**What `core.autocrlf` does (general Git behavior; WSL setting checked 2026-10-18):** CRLF and LF are two ways a text file can mark the end of a line. With `core.autocrlf=true`, Git converts CRLF to LF when it commits a text file and changes LF back to CRLF in the working folder; the Git Bash warning `LF will be replaced by CRLF` describes that conversion. In WSL, `core.autocrlf` was unset. That setting does not convert line endings; unless a repository attribute sets another conversion rule, CRLF working files can appear changed against Git's LF index. This fits WSL's output, but the cause is unconfirmed because changing the setting was not tested.

**Submodule changes that are only line endings (reported from terminal output, 2026-10-18):** In `git submodule status`, a leading space means the submodule is at the commit recorded by the parent repository; a `+` means it is at a different commit. `git -C vprofile-src status --short` lists changed files inside the submodule, and `M` means a tracked file differs from Git's stored version. The full status list had no entries beyond unstaged ` M` changes, and `git diff --ignore-cr-at-eol --stat` showed no remaining text differences in those tracked files. Together these results fit line-ending-only changes in `vprofile-src`, but do not prove that cause. Nothing was restored; do not run `git restore` in the submodule just to clear these marks, because it rewrites files without need.

**Checking a branch before using it (verified from terminal output, 2026-10-17):** `git switch -c <name>` creates a branch at the current commit and keeps uncommitted working-tree edits; `git switch <name>` stops if switching would overwrite them. `git log main..<branch>` lists commits on that branch but not on `main`; no output means there are no branch-only commits. `git diff --stat main <branch>` compares the two snapshots, so an older branch can show deletions because it lacks newer lines from `main`. In this project, `docs/update-progress-notes` had no commits that `main` lacked, and its large diff reflected its older snapshot; this says nothing about uncommitted changes on that branch. `git branch -d` deletes a branch only when Git considers it merged; `-D` forces deletion, so check first.

**Checking files before a public commit (reported from terminal output, 2026-10-17):** `grep -c "text" file` counts lines containing the text without printing the matched lines. The scan reported 0 matches for the AWS account number and Identity Center user name in the five files checked. AWS `AccessDenied` messages can expose account or principal details, so describe the error in words and keep raw output private unless it is sanitized. A zero count checks only those exact strings in those files; it does not prove that other files contain no sensitive information.

**The Git pager:** Git may show long output one screen at a time; press `q` to leave the pager. `git --no-pager <command>`, such as `git --no-pager diff --stat NOTES.md`, prints the command's output without opening it.

**A submodule pin, a branch, and a tag:** The Project 3 submodule points to one exact VProfile commit, `9f22748`. A detached HEAD means Git has checked out that commit without putting the folder on a branch; a branch can move to later commits, while a tag is a name meant to stay on one commit. A remote branch or tag can keep the commit reachable for future clones while that reference exists, so check source-use permission before publishing a tag.

**Surefire and test engines:** Surefire is the Maven plugin that runs tests. JUnit 4 and JUnit 5 are different test systems, and the Vintage engine lets JUnit 5 run JUnit 4 tests. The linked [Surefire 3.6.0 guide](https://maven.apache.org/surefire-archives/surefire-LATEST/maven-surefire-plugin/whats-new-3-6-0.html) is reported to say the plugin automatically adds Vintage for JUnit 4; that guide was not independently reviewed. The PR #2 run comparison is consistent with this report, but does not prove which engine loaded in either run. `mvn dependency:tree -Dincludes=org.junit.vintage` showed no Vintage engine in the project's dependencies, but that does not show what Surefire adds on its own.

**Commands used:** `git show <commit> -- <file>` shows what one commit changed in one file. `git fetch --prune` removes local pointers to branches deleted on GitHub (it printed `[deleted] ... origin/test/failure-path`). `git branch -d` deletes a branch only if it is merged, and `-D` forces it. `git switch -c <name>` creates and enters a new branch. `git status -sb` prints a one-line branch summary. `cut -c1-100` trims long lines so output stays readable.

`git diff --stat` shows only how many lines changed, while `git diff -U0` shows the changed lines with zero unchanged context lines; the count alone cannot show that the right text was saved. `fold -w 150` wraps long lines for reading. `git restore <file>` discards uncommitted edits in that file. `git diff --cached` shows what is staged (selected for the next commit).

**Searching and reading files:** Recursive `grep` searches files under a folder and prints matching lines; no matches means the search found no matching text in that scope. `sed` can display selected lines, while `cat` prints a whole file, so check file output for credentials before sharing it.

**Login shell and `PATH` (verified):** `PATH` is the list of folders a shell searches when you type a command. A command can be installed but not found if its folder is missing from the current shell's `PATH`. Ansible was found in WSL Ubuntu's login shell; a `command not found` result from a non-login shell did not prove it was uninstalled.

**Current folder and relative paths (verified):** A relative path such as `vprofile-src/...` starts from the current folder. It can fail from the Ubuntu home folder even when the file exists in the repository, so check the working folder before using a relative path.

**Reading AWS settings safely (verified):** The AWS setup check showed section and setting names only, not credential values. Read only the names needed to understand the profile; displaying credential files can expose secrets.

**WSL distributions and shell installs (verified):** WSL distributions are separate Linux environments. Use Ubuntu WSL for the project tools; `docker-desktop` is a different distribution. Git Bash is a separate Windows shell with its own tool installations and AWS settings. Installing Terraform in Ubuntu WSL does not update or replace the Git Bash copy.


**Installing software with apt and a signing key (verified 2026-10-10):** `apt` is Ubuntu's tool for installing software from lists of packages. HashiCorp signs its list with a key, and a fingerprint is a short ID computed from that key; if the saved key's fingerprint equals the one HashiCorp publishes, the key is the real one. In this project the saved key's fingerprint matched the published value (the source for the published value was not independently checked), then `apt update` and `apt install terraform` put Terraform v1.16.5 in Ubuntu WSL.

**Using sudo in WSL (verified 2026-10-10):** `sudo` runs a command with administrator permissions. For a command that needs a password, use the real Ubuntu terminal if launching it through Git Bash does not show the prompt. The failed and successful attempts are recorded in `PROGRESS.md`.

**Loopback address and security group (planned; not configured):** A service listening only on `127.0.0.1` accepts connections from the same computer. A security group with no inbound rules blocks new incoming connections, while its stateful behavior allows replies to permitted connections; SSM works because the instance's agent starts an outbound connection. The one-instance design needs both controls, and Ansible must set each service's bind address because package defaults are partly unverified. Loopback is the planned bind for this layout because other computers cannot reach the service even if a security-group rule is accidentally added. A multi-instance layout would need network-address binds and security-group rules limited to the app host (planned; not tested). On Linux, `127.0.0.2` is normally also a loopback address (not checked for this app); see the Memcached note for what the code reading does and does not establish.

**Memcached active and standby hosts (reading of the code, not a tested run; 2026-10-10):** Memcached is a program that keeps recent data in memory so the app can read it quickly. VProfile is configured with an active host, `mc01`, and a standby, `127.0.0.2`. The app first connects to `mc01` and asks for the server's process ID; if that works, it uses `mc01`, and only if it fails does it try `127.0.0.2`. On one instance, `mc01` and the app point to the same host, which would leave the standby unused. What the app does if both fail was not seen. What happens if the active host throws an error was not seen.
