## Problem and constraints

Project 3's earlier Phase D design applied to a different account and cannot be carried into the new account as approval. The new-account plan must keep the state bucket separate from application teardown, stay within the account and credit safeguards, avoid public WAR distribution, and make the running application stack inexpensive to stop between sessions. The new-account design also needs its own cost and implementation gates.

## Planning baseline

Use the existing bootstrap Terraform root for the state bucket. Add separate durable and ephemeral application roots with separate state keys. The durable state key `durable/terraform.tfstate` was proposed; the ephemeral state key `ephemeral/terraform.tfstate` was chosen for planning on 2026-10-23. Each backend key must match the final configuration before implementation.

| Layer | Planned ownership | Lifecycle |
| --- | --- | --- |
| Bootstrap | Existing Project 3 state bucket and bootstrap settings | Remains separate; not part of application teardown |
| Durable | WAR bucket, Ansible-transfer bucket, GitHub OIDC provider, deploy role, instance role and profile; role-specific boundary policies are referenced by ARN but created outside this layer (see the boundary-policy ownership decision) | Retained between sessions; removed only during separately approved project teardown |
| Ephemeral | VPC, private subnet, routing, NAT path, security group with no inbound rules, and one EC2 instance | Created for a work session and destroyed afterward; destroy must not affect durable resources or IAM |

The deployment flow is planned as GitHub Actions building the WAR, uploading it to the private WAR bucket, Ansible running from the GitHub runner over SSM using the transfer bucket, a health check, and rollback to a prior WAR version. This flow is not implemented or verified in the new account.

## Planning choices and trade-offs

- **One `t3.large` and a 20-GiB encrypted gp3 root volume.** One host is easier to manage than four `t3.small` instances with similar total memory. Capacity is unverified, and sustained CPU use may incur surplus-credit charges.
- **Private subnet with NAT.** This avoids a public address on the instance and preserves the planned outbound package path. NAT access to package repositories has not been verified in the new account. Three interface endpoints were estimated cheaper for short sessions, but required endpoint coverage and package-site access are unknown; the public-subnet option is cheaper but exposes a public address. See the dated estimates and source limits in [PROGRESS-HISTORY.md](../../PROGRESS-HISTORY.md).
- **Defer S3 server access logging.** The durable bucket code has no access-logging configuration. The two `terraform:S6258` findings on PR #66 were later reported Accepted with the reason that logging is deferred for this single-owner portfolio project; this accepts reduced request-audit history and does not fix or enable logging. Do not confuse these two findings with the earlier prior-account D1 findings, whose recorded status remains separate. See the 2026-10-24 checkpoint below.
- **Run Ansible from the GitHub runner over SSM.** This avoids SSH ingress and keeps deployment within the proposed workflow. The runner plugin, exact SSM documents, network path, and interrupted-run behavior remain unverified.
- **Defer Jenkins until GitHub Actions deployment works.** Jenkins remains required before Project 3 is complete; J1 versus J2 is undecided. The long-term direction is parity with one platform operating the flow at a time, not simultaneous deployment.

### Problem

### Decisions

1. **GitHub Environment `production`, restricted to `main`.** The trust policy checks the audience, the environment subject, `ref`, `environment`, `repository_id` and `repository_owner_id`. This repository uses immutable subject claims (reported by the author from the repository's OIDC settings page), so subject strings carry owner and repository IDs.
2. **Working assumption: Ansible runs on the GitHub runner with the `aws_ssm` connection plugin.** Under it the deploy role needs `ssm:StartSession` and no `ssm:SendCommand`. Current `amazon.aws.aws_ssm` documentation says the controller uses presigned S3 URLs and the managed instance needs no S3 IAM credentials for that documented transfer path. The project’s selected collection version, plugin configuration, and end-to-end transfer remain unverified; the instance still needs S3 network access and `curl`. See [Open items and approval limits](#open-items-and-approval-limits) for the remaining transfer-bucket and policy checks.
3. **Option 2 for `p3-terraform`:** an explicit deny of `iam:UpdateAssumeRolePolicy` and `iam:DeleteRole` on `p3-vprofile-deploy`, added to the durable policy that root attaches. Blocking only the trust update would not help, because deleting and recreating the role also sets its trust.
4. **Boundary scope:** the local instance-boundary draft matches instance permission policy v2 and excludes `ssm:GetParameter` and `ssm:GetParameters`; the deploy-boundary draft matches deploy permission policy v1 (8 statements). Session 1 reports creation of AWS boundaries with the expected names, counts, and Sids, but their saved contents were not compared line by line with these drafts. Under option B, later boundary changes require a separately approved root session. The full drafts are in the [redrafted-boundaries section](../drafts/new-account-iam-policy-package.md#2026-10-23-redrafted-permissions-boundaries-review-only-planning).

### Alternatives considered

- **No Environment (branch subject only):** simpler and needs no GitHub setup, but gives no approval pause and relies on the AWS trust policy alone.
- **Option 1, accept the risk (leave `p3-terraform` able to change trust):** least work, but a stolen or mistaken session could remove the `main` and Environment checks.
- **Option 2b, root creates the deploy role and its trust:** no explicit deny is needed and Terraform only references the role, but the role sits outside Terraform state and teardown has a manual step. Not selected; may be revisited.
- **Option 3, root creates both roles:** most root sessions and manual work.
- **Sending commands with SSM documents instead of the plugin:** not selected; it would not let Ansible run from the runner.

### Consequences and accepted trade-offs

- A wrong trust policy at the first apply can be fixed only by a root session, so the environment `sub` string must be confirmed before that apply.
- Destroying the durable layer fails at the deploy role and needs a root session.
- The instance role stays fully under Terraform; that risk is accepted as part of option 2 as described.
- Both permissions boundaries were redrafted on 2026-10-23 to match the narrowed role policies, without headroom. The local texts remain review artifacts; session 1 reports that matching named policies were created, but the saved JSON was not compared line by line. Review the text before Terraform later creates roles that use the boundaries.

## 2026-10-23 — Ansible transfer bucket stays unversioned (planning only)

- **Decision (author-confirmed, 2026-10-23 planning choice):** the Ansible transfer bucket is to be unversioned.
- **Reason:** the `aws_ssm` plugin deletes its temporary transfer files after use. With versioning on, a delete only adds a delete marker and older versions remain. Deploy permission policy v1 has `s3:DeleteObject` but not `s3:DeleteObjectVersion`, so the deploy role could not remove them.
- **Requirement for implementation:** the durable-layer Terraform must not enable versioning on this bucket. Read back the versioning state after creation.
- **Not decided:** the WAR bucket's versioning is a separate question.
- **Status at the 2026-10-23 checkpoint:** not applied and no AWS bucket setting had been checked. The later author-supplied versioning read is recorded in the 2026-10-24 apply checkpoint below; it returned no output/status and was interpreted as versioning never enabled.

## 2026-10-23 — Durable-bucket policies applied by root, not `p3-terraform` (planning only)

- **Decision (author-confirmed, planning only):** `p3-terraform` has no write access to bucket policies on the WAR and Ansible transfer buckets. The durable Terraform declares no bucket-policy resource for them.
- **Reason:** Block Public Access limits public exposure but does not enforce HTTPS. The HTTPS-only control is the `aws:SecureTransport` condition in the bucket policy. Replacing a bucket policy can also change more than that rule. Denying only `s3:DeleteBucketPolicy` would leave `s3:PutBucketPolicy` open, so no deny is used.
- **Draft change:** `s3:PutBucketPolicy` is removed from `ManageDurableBuckets` in the option-B copy. `s3:DeleteBucketPolicy` was never in it. `s3:GetBucketPolicy` is kept, because the provider may read the policy during refresh (an unverified inference).
- **Sequence:** Terraform creates the buckets, and nothing uses them. A separately approved root session applies the HTTPS-only policies and reads them back. Deployment use is allowed only after that read-back succeeds.
- **Consequences:** the policies are outside Terraform state. The author owns future checks and changes, each through a root session. Any future bucket policy must not grant access to `p3-terraform`.
- **Unverified:** the effective permissions of `p3-terraform` (the role cannot read its own policies) and whether the provider needs `s3:GetBucketPolicy`. The first plan is the real test.
- **Status:** not applied. No AWS check or change was made. This supersedes the earlier undecided status for `s3:PutBucketPolicy` on the two durable buckets. The bootstrap state bucket's separate temporary acceptance is unchanged.
