## Decisions

- **Pipeline:** designed from scratch. Do not inspect, consult, copy, or derive the design from the instructor's `Jenkinsfile` or other instructor pipeline file. If one becomes necessary to answer a specific unresolved question, explain why and get the user's approval before accessing it.
- **Application:** VProfile is instructor-provided, not written by the repository author.
- **Scope and order:** Phase 1 GitHub Actions, then Phase 2 Jenkins (required before the project is complete). Both are meant to run the same build and deployment flow against the same target, one tool at a time. Within Phase 1, build/test comes first and AWS deployment is added only after its design and cost gate.
- **Repository:** public; holds the author's pipeline code, infrastructure code, and documentation, with VProfile referenced through a pinned submodule in the current local checkout. No credentials, account identifiers, built WARs, or VProfile source contents in workflow logs. The submodule URL points to the author's fork; source-use permission remains unresolved.
- **Branch strategy:** use `main` plus short-lived pull-request branches. No reviewer requirement was reported. The active `protect-main` ruleset and its reported settings are documented under **Main ruleset** above.
- **Triggers:** `pull_request`, `push` to `main`, and `workflow_dispatch`. Phase 1 runs are build/test only with no AWS access.
- **Zero-test fix location (approved 2026-10-01; necessity under review, approval not withdrawn):** Option B remains the recorded design: pin an unmodified VProfile commit and apply the `junit-vintage-engine` change to the build copy from one shared script; fail unless Maven reports a positive test count. The local run with the insertion reported 9 tests. In PR #2, the first run had that insertion commented out yet still reported 9 tests under Surefire 3.6.0; a later run reported 0 tests, but its count pattern had been changed to the literal `99999`. The 9-versus-0 difference is strongly supported to coincide with the runner image changing the effective default Surefire version (see **Failure-path experiment**), so the Vintage insertion is retained to cover the older Surefire behavior; this is not a proven root cause. The Surefire 3.6.0 guide ([guide](https://maven.apache.org/surefire-archives/surefire-LATEST/maven-surefire-plugin/whats-new-3-6-0.html); not independently reviewed) is reported to say that Surefire 3.6.0 automatically adds the Vintage engine for JUnit 4 tests; this fits the run comparison, but the logs do not identify the engine loaded in either run. See **Failure-path experiment** and NOTES. Keep the approved insertion; any change still needs user approval.
